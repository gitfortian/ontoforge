## 1. T5 发现并实际修复的四类 P1 语义缺陷

1. **P1-T5-01 / 物理扫描预算证据少算 BRIDGE**：此前 `LinkTraverseService` 的 `budget.physicalRows` 只加 SOURCE+TARGET 两表，即使第三表扫描计入了内层 `Budget.accept`，对外证据却不完整；现修正为 SOURCE+TARGET+BRIDGE **三表物理行总数**。真实 PG17 夹具 2+5+13=**20**，受检 HTTP 结果精确断言 20，而非 7。
2. **P1-T5-02 / 重复 Pair 统计越出根作用域**：旧 `bridgeDuplicatePairRowCount` 遍历整个 Bridge，包括本次请求未选择 root 的有效 Pair，违背 R2 仅披露 `TRAVERSAL_SCOPE` 中实际匹配 Pair 的合同。现只在选中根对象且匹配输出端过滤条件、两端存在的 Pair 上去重计数；真实 PG17 同时制造根 `EQ-001` 的 2 个重复物理 Pair 行，以及无关 `EQ-002` 的 1 个额外重复，分别查询得出 2 和 1，绝不从全局 3 泄露不相关结果。
3. **P1-T5-03 / 重复孤儿抬高 knownOrphanCount**：旧 Bridge 迭代对同一孤儿物理 Pair 重复计数，造成 `PARTIAL` 品质失真。现利用 `Pair(source,target)` 值语义去重，仅在当前 root 真正有一侧可核验时计 1；真实 fixture `(EQ-001,LOT-NO)` 重复两行但 `knownOrphanCount=1`，其它 root 不受影响。
4. **P1-T5-04 / 空主键身份不可编码**：PG 的非 NULL TEXT 主键可取空串，但 M6 ObjectRef `key.value` 严禁空值。旧 Bridge FULL `readKeys` 允许空字符串通过；现明确校验空白/超长主键 → **409 OBJECT_IDENTITY_UNREPRESENTABLE**，不能误判为 SQL NULL、孤儿或 VALID。新增真 PG17 TEXT PK `''` 的 `POST FULL`、`POST Traverse` 负例；错误响应无实体数据载荷。

**额外 P1 负例：DDL 指纹漂移后签名游标不能复活。** 真 PG17 `ALTER TABLE public.m8_equipment_inspection_bridge ADD COLUMN t5_schema_probe TEXT` 后，原 FULL 指纹不再符合，请求 FULL 409，读取历史 Bridge Revision/Traverse/Page 受控拒绝；移除该列恢复结构后，先前漂移失效的签名 Cursor 继续 410，不能自动恢复。整个测试过程中旧 FK 历史 Revision 未修改。

**实际改动路径**：[LinkTraverseService.java](../../ontoforge-business/src/main/java/io/ontoforge/business/query/LinkTraverseService.java)、[BridgeLinkBindingService.java](../../ontoforge-business/src/main/java/io/ontoforge/business/connection/BridgeLinkBindingService.java)、[LinkBindingFullIntegrationTest.java](../../ontoforge-boot/src/test/java/io/ontoforge/boot/LinkBindingFullIntegrationTest.java)。本修订保留 R1/R2 合同与旧 M8.1 已有正反例，没有删门禁绕过失败。

## 1.1 T5 随后追加的真实数据库并发、冻结分页与字节限额反例

- **合法 0 边**：给真实 SOURCE 增加一个无 Bridge 关系的有效端点 `EQ-003`，OUT 返回 HTTP 200 / COMPLETE / 0 objects / 0 links、当前三表物理预算 21，删除该行后恢复原 fixture；无边结果不能被猜成 PARTIAL 或失败。
- **Bridge CAS 同 Head 并发**：两条实际 Spring HTTP UPDATE 使用同一 revision=2、不同 Operation UUID，由两个并发线程同时提交；预期 **一个 200 revision3，一个 409**，在 `runtime_link_binding_revision` 仅有一条 revision3、共享 `runtime_link_binding.current_revision=3`。这是同一 JVM / 真实 PostgreSQL 行锁与事务 CAS 的证据；**不能冒充不同 JVM、多 Worker 网络故障竞态**。
- **源事实 DML 更新 vs 已签名 frozen page**：签发 OUT 查询第一页后，数据库真实删除 Bridge 中两条 `EQ-001→LOT-12` 记录；此时重新执行 ObjectSet 查询只能得到剩余一个对象、物理扫描 18 行，但**旧签名 page2** 仍在有效 TTL 与当前授权下返回最初冻结的第二对象、旧预算 20 行。随后恢复两条 Bridge 记录以不影响其它测试。这证明冻结结果不会跟着实时表数据静默重算，也没有谎称历史 PostgreSQL 快照仍存在。
- **真实三源读取的字节预算**：对相同 OUT 查询降低 `limits.maxSourceBytes=64`，三表扫描超出来源 UTF-8 字节额度必须返回 HTTP 429 `QUERY_BUDGET_EXCEEDED`、不得带回任意 Bridge 表名或对象键；仍缺 8MiB 上限附近真实大值与 3s source lock 竞争压力。
- 这些用例均补在 [LinkBindingFullIntegrationTest](../../ontoforge-boot/src/test/java/io/ontoforge/boot/LinkBindingFullIntegrationTest.java) 并由真 PostgreSQL 17 / Spring HTTP 驱动。**在最新提交 CI 真正 completed/success 之前，上述仅是已经提交的可证伪断言，不预写验收成功。**
