# OFIP-0005 P0-B · UX-High 模型治理高保真交互设计与验收矩阵

> 阶段：**UX-High / Design Review Candidate**  
> 对应：OFIP-0005 / PR #16  
> 本轮性质：**产品交互定稿候选，不是真实治理功能**  
> 原型：doc/prototypes/ofip-0005-governance-highfi.html  
> 浏览器检查：doc/prototypes/tests/test_ofip0005_governance_highfi.py  
> 重要边界：原型仍使用浏览器内存 Mock，不调用真实 API / PostgreSQL，不执行真实审核、正式版本创建或生效。

## 1. 本轮要解决的产品问题

UX-Low 已经把“模型变更 → 审核 → 正式版本 → 生效 → 回退”流程跑通，但仍然偏结构化草图。

UX-High 本轮只做一件事：

> **把这条流程变成可以直接作为未来 React 产品视觉与交互目标的页面。**

同时解决三个长期问题：

1. 用户第一眼看到的是**业务状态**，而不是技术对象；
2. 页面风格必须与当前 OntoForge Studio 一致，不能再出现“孤立的专业工具 Demo”；
3. 每一个关键动作都必须告诉用户：**现在是什么、做了以后会怎样、如果失败下一步去哪里。**

---

## 2. 高保真产品信息架构

不新增“治理中心”“版本中心”等独立技术菜单。

    OntoForge / 本体设计
    └── 模型包：manufacturing.production
        ├── 概览
        ├── 我的变更
        ├── 待我审核
        ├── 正式版本
        ├── 生效范围
        └── 治理记录

这些页面是同一个“模型包治理工作区”的不同工作状态。

未来真实 React 应沿用现有 OntoForge Studio：

- 左侧统一导航；
- 蓝灰色视觉体系；
- 卡片、表格、状态标签；
- 页面顶部上下文；
- 底部固定操作区；
- 异常状态在当前页面内给出恢复路径。

## 3. 六个核心页面

### 3.1 模型包概览

第一眼回答：

- 当前正在使用哪个版本？
- 有没有待处理事项？
- 最近发生了什么？
- 我现在能做什么？

示例：

> 当前生效版本：**0.4.0**  
> production-core 正在使用  
> 待我审核：**1 项**

不把 Snapshot ID、Digest、CAS、revision 放在首页。

### 3.2 我的变更

回答：

> 我提交过什么？现在走到哪一步？

每项变更显示：

- 业务名称；
- 基线版本；
- 具体变化摘要；
- 提交人；
- 当前状态；
- 风险；
- 下一步。

主动作：

> **准备模型变更**

提交前明确：

> **提交以后，这份变更内容会固定。**

### 3.3 待我审核

回答：

> 哪些事情现在需要我判断？

只显示：

- 当前身份有审核权限；
- 且不是本人提交。

审核详情采用：

**改了什么 → 为什么改 → 有什么风险 → 检查结果 → 审核依据 → 作决定**

不能让“批准”成为页面第一视觉焦点。

### 3.4 正式版本

回答：

> 哪些版本已经经过治理，可以被业务范围使用？

必须持续区分：

| 状态 | 含义 |
|---|---|
| 已发行 | 已形成受治理的正式版本 |
| 当前生效 | 某个业务范围正在使用 |
| 尚未生效 | 已发行，但尚未被任何范围切换使用 |
| 历史版本 | 仍可信、可追溯，可作为回退目标 |

核心文案：

> **创建正式版本不会自动让任何业务范围切换。**

### 3.5 生效范围

回答：

> 哪个业务范围正在使用哪个版本？我要把它切换到哪个版本？

必须同时显示：

**范围 + 当前版本 + 目标版本 + 生效原因**

确认前再次核对当前版本。

如果发现版本已经被其他操作改变：

> **当前生效版本已经变化，请刷新后重新确认。**

不能静默覆盖。

### 3.6 治理记录

回答：

> 这次模型变化完整经历了什么？

按时间展示：

**提交 → 检查 → 审核 → 正式发行 → 生效 → 回退**

每一步都能回答：

- 谁做的；
- 什么时候；
- 基于哪个版本；
- 为什么；
- 结果是什么。

## 4. UX-High 视觉层级

### 一级信息

业务人员第一眼必须看到：

- 模型包名称；
- 当前生效版本；
- 变更状态；
- 风险；
- 下一步。

### 二级信息

需要判断时再看到：

- 原版本 / 候选内容；
- 具体对象、属性、关系变化；
- 检查结果；
- 生效范围；
- 审核意见。

### 三级信息

只供研发/审计定位：

- 稳定 ID；
- 模型路径；
- 内容摘要；
- revision；
- 幂等请求信息；
- 技术错误码。

原则：

> **技术信息可以存在，但不能主导产品界面。**

---

## 5. 状态语义统一

| 用户状态 | 推荐显示 | 不推荐 |
|---|---|---|
| 草稿 | 模型草稿 | Draft |
| 正在审核 | 等待审核 | REVIEW_PENDING |
| 审核通过 | 审核通过 | APPROVED |
| 已正式发行 | 已发行 | RELEASED |
| 尚未切换 | 尚未生效 | INACTIVE |
| 正在使用 | 当前生效 | ACTIVE |
| 影响无法判断 | 消费者影响未知 | UNKNOWN |
| 请求结果未知 | 操作结果暂时无法确认 | RESULT_UNKNOWN |
| 版本冲突 | 当前版本已经变化 | CAS_CONFLICT |
| 无权限 | 当前身份没有执行权限 | FORBIDDEN |

## 6. 高保真关键交互

### H01：进入模型包

看到：

> manufacturing.production  
> 当前生效版本 0.4.0

而不是看到技术资源 ID。

### H02：准备模型变更

右侧抽屉打开，不离开当前上下文。

填写：

- 基线版本；
- 候选内容；
- 业务原因。

### H03：提交前固定内容

必须出现明确提醒：

> 提交以后，这份变更内容会固定。之后继续编辑模型不会改变正在审核的内容。

### H04：审核

审核详情必须先展示 Diff，再展示风险，再展示决策。

### H05：审核结果

- 批准：允许进入正式版本创建；
- 退回修改：保留审核依据，提交人修改后重新提交；
- 拒绝：当前审核轮次结束，需要重新提出变更。

### H06：创建正式版本

确认页显示：

- 模型包；
- 版本；
- 变更；
- 审核人；
- 当前生效版本。

并明确：

> 正式版本 ≠ 当前生效版本。

### H07：生效

确认：

> production-core  
> 0.4.0 → 0.5.0

填写原因。

### H08：生效竞态

服务端再次核对旧版本。

如果别人已经切换：

> 本次操作拒绝，不覆盖最新版本。

### H09：生效超时

浏览器没有收到回执：

> **不要重复点击。**

进入：

> 核对当前生效版本

### H10：回退

不是“撤销发布”。

而是：

> **切回历史版本 0.3.0**

并产生新的治理记录。

## 7. 高保真验收矩阵

| 编号 | 实际浏览器动作 | 用户必须理解的事实 | 结果要求 |
|---|---|---|---|
| H01 | 打开页面 | 当前版本是什么 | 页面首屏明确显示 0.4.0 |
| H02 | 查看导航 | 治理是一条工作流，不是技术菜单 | 六个工作区入口 |
| H03 | 打开我的变更 | 变更状态是什么 | 等待审核/草稿清楚 |
| H04 | 打开提交抽屉 | 提交需要业务原因 | 空原因不能提交 |
| H05 | 查看提交提醒 | 提交后内容固定 | 明确提示 |
| H06 | 打开待审核 | 为什么这条给我审核 | 角色与权限边界明确 |
| H07 | 打开审核详情 | 先看改了什么 | Diff 位于决策之前 |
| H08 | 查看技术定位 | 技术信息是二级信息 | 可折叠 |
| H09 | 点击批准 | 批准后发生什么 | 显示进入正式版本阶段 |
| H10 | 点击退回 | 退回后怎么办 | 修改并重新提交 |
| H11 | 查看正式版本 | 正式版本不是生效版本 | 两种状态同时可见 |
| H12 | 创建正式版本 | 创建版本不会自动生效 | 确认页再次提醒 |
| H13 | 进入生效范围 | 影响哪个业务范围 | 范围业务化展示 |
| H14 | 空原因确认生效 | 必须填写生效原因 | 页面内错误提示 |
| H15 | 正常确认生效 | 会切换哪个版本 | 旧版→新版明确 |
| H16 | 模拟回执丢失 | 不能重复操作 | 恢复路径明确 |
| H17 | 查询当前状态 | 超时后先核对真实状态 | 不冒充成功 |
| H18 | 切回历史版本 | 回退不是删除版本 | 新生效记录 |
| H19 | 查看治理记录 | 谁做了什么 | 完整时间线 |
| H20 | 390px 浏览 | 页面不发生横向溢出 | 主任务仍可操作 |

## 8. 本轮真实浏览器检查边界

浏览器测试只证明：

> **高保真原型的页面和用户操作路径成立。**

它不证明：

- OIDC；
- RBAC；
- PostgreSQL；
- ChangeSet；
- Review；
- Release；
- Activation；
- SHA/JCS；
- 真实权限拒绝；
- 生产消费者兼容。

所以 H01–H20 全部 PASS，也只能让：

> **UX-High = 设计验收候选**

不能让：

> **P0-B = 功能完成**

## 9. 高保真签收门槛

进入 B0 真实身份/权限实施前，必须满足：

- [ ] H01–H20 Chromium 全部 PASS；
- [ ] 与现有 OntoForge Studio 视觉体系一致；
- [ ] 一级产品术语没有技术对象泄漏；
- [ ] “正式版本”和“当前生效版本”不会混淆；
- [ ] “切回历史版本”不会被理解成撤销业务操作；
- [ ] 所有异常都有下一步；
- [ ] 无权限、版本冲突、请求超时三类错误表达不同；
- [ ] 技术详情全部降为二级/三级信息；
- [ ] 未来 React 开发可以逐项映射 H01–H20。

**全部满足后，UX-High 才可以申请正式签收。**
