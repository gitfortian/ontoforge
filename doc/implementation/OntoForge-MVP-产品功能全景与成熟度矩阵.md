## 1. 五条产品成熟度边界：必须说清哪个 MVP

| 范围 | 解决的真实问题 | 用户最终应看到的效果 | 当前状态 |
| --- | --- | --- | --- |
| **S0 工程基础 MVP** | 单人本地模型能保存、校验、留存历史吗？ | 建模工作台创建对象及关系，校验后留存两份不可修改的版本并比较差异 | **0.3/0.4 已合并；隔离环境自动化见第 10 节；用户既有安装验收与正式发布未完成** |
| **P0 专业建模 MVP** | 领域专家能否完整定义对象及关系，并可信审核发布？ | 建批次/订单/质量事件与关系 → 校验 → 审查 → 正式发布/读取/回退 | **尚未完成**；S0 只覆盖其一部分 |
| **P1 工业业务价值 MVP** | 能否跨真实业务系统查询对象与关系？ | 绑定受控 QMS/MES/ERP 测试数据，找出异常批次影响哪些订单及依据 | **未实现产品**；部分查询研究 POC 不能计入 |
| **P2 Agent 增强 MVP** | Agent 能否读到有权限、有证据、可追溯的真实业务上下文？ | Agent 通过 SDK/MCP 只读查询批次、工单和影响订单，并引用来源和数据时效 | **未实现** |
| **P3 受控行动 MVP** | 审核后能否安全处置，并确认外部系统真实结果？ | 展示操作计划 → 权限/审批 → 沙箱调用 → 回执/未知态/结果核验 | **未实现**；Outbox 研究实验不算交付 |

P0 是**建模产品可用门槛**，P1 才是**工业业务价值开始成立的门槛**；P2/P3 是后续能力。不能把当前 S0 版本称为面向工厂可用的工业本体平台。

## 2. “最基础”与“完善”的判定口径

| 层级 | 如何判定 | 报告中的表述 |
| --- | --- | --- |
| 未实现 | 只有想法、需求或架构草案，无真实用户功能 | 未实现 |
| 研究验证 | 有 Schema 合同、实验代码、Mock 原型，但未接通真实产品流程 | 已研究/已验证部分风险，**不是功能完成** |
| **基础可用** | 在有限范围内完成真实页面/接口/数据保存与关键错误路径 | 基础可用，说明**具体子功能** |
| **基础可用·加固** | 在基础场景上验证过并发、异常、完整性等高风险边界 | 该子场景可靠性加固，**不是全域完善** |
| **专业完善** | 对象、关系、权限、依赖、审查、发布、业务异常等核心场景均打通 | 专业功能较完整，仍需正式环境验收 |
| 生产验收 | 完成身份/数据安全/运维/规模/故障恢复等实际环境验证 | 在限定部署边界内可试点/上线 |

**两轴原则**：功能覆盖范围和技术可靠性单独报告。比如 0.3 的历史快照可靠性好，但 F04「版本发布」的正式审批、发行和激活仍为**未实现**，不得将 F04 标为完成。不得凭通过测试的数量推算全局完成百分比。

## 3.2 M4 Runtime Type Catalog：通用类型解析与只读目录（PR #56）

**产品目的**：把已有 Native ObjectType 定义转成运行时可读取、可被后续模块稳定引用的类型描述。M4 交付的是“类型合同可被通用运行时理解”，不是“已存在的业务对象可查询”。

| 交付能力 | 实际行为 | 当前边界 |
| --- | --- | --- |
| 草稿类型解析 | 只有请求的 draftId + revision 与当前 revision 一致、校验状态为 VALID 且 validatedRevision 匹配时，才重新生成 Native Candidate 并返回类型描述 | 草稿保存后旧 revision 返回 409；不隐式重定向到 latest |
| 快照类型解析 | 通过现有 Snapshot Service 核验 RFC 8785/JCS 字节、SHA-256、JSONB 镜像和 Native Schema，再返回不可变类型描述 | 仅 LOCAL_SNAPSHOT_ONLY，不代表正式发布 |
| 只读 API | 提供草稿/快照各自的类型列表与详情，共 4 个 GET 接口 | 复用现有 /api/model/** 安全域及包授权；不新增 Registry 表或 Flyway 迁移 |
| Property 合同 | 展示稳定 ID、API 名称、类型、必填、可检索、分类、枚举值和主键引用 | 主键不会自动推导 searchable=true；不返回对象实例或来源事实 |
| 工作台入口 | 从有效草稿或本地快照进入统一只读目录，显式切换可用来源 | 不复制第二套 ObjectType 编辑器；来源不可用/无权限时显示错误，不伪装为空成功 |
| 自动化验收 | [PR #56](https://github.com/gitfortian/ontoforge/pull/56) 包含真实 PostgreSQL 17 HTTP/JUnit 正反例、React 构建与 Chromium 黄金故事 | 自动化通过不代替用户既有 Windows 安装人工验收，也不代表生产发布 |

**功能成熟度**：M4 类型目录是 F02/F03/F04 的基础子能力。它为后续 Data Binding 锁定类型版本、为 ObjectSet 建立字段类型约束提供稳定入口；它本身不实现 Data Binding、ObjectFact、ObjectSet 查询、正式 SchemaRelease/Activation、Action 或 Agent。上述后续能力不得因为 M4 完成而标记为已实现。

### M5 生产实现检查点（2026-10-18，PR #63）

**本轮真实交付**

- 后端与 V7 数据迁移：通用 Binding、不可变 revision、CAS 更新、JCS/SHA-256 摘要、来源 schema fingerprint、数值精度/长度指纹、稳定排序与来源结构漂移拒绝。
- 来源安全：独立只读登录/角色、限定表 allowlist、loopback 同库同端口约束；真实 PostgreSQL 验证 SELECT 可用，INSERT/UPDATE/DELETE/DDL 被拒绝；只读账号仍能从 PostgreSQL 系统目录正确读取主键与单列唯一约束。
- 映射合同：来源身份键必须是主键或单列唯一键；DECIMAL 不接受浮点列；INTEGER 以规范十进制字符串传输，避免 JavaScript 大整数精度损失；ENUM 只接受受控文本值；结构精度变化会触发 drift。
- 用户闭环：创建自定义 ObjectType → Local Snapshot → 来源目录 → 映射 → 预览 → 有界校验 → 保存 → 重开历史。修改来源身份键会生成新 identityDomainId，页面明确提示旧 ObjectRef 不会自动重定位。
- 持久化证据：真实后端重启后，revision 1/2 的摘要、快照引用与 identity domain 均与重启前一致；旧 revision 保持不可变。

### P0-B 这轮用户体验原型到底完成了什么

用户现在可以在低保真原型里完整走通：

**模型包概览 → 准备模型变更 → 提交审核 → 审核变更 → 创建正式版本 → 选择生效范围 → 确认生效 → 治理记录 / 超时恢复 → 历史版本回退**

但这些动作目前是**浏览器内存演示**。它证明的是产品流程是否合理，不证明 Java/PG/React 生产功能已经实现。

### P0-B 与全局 P0 的关系

P0-B 不是一个孤立的“审批模块”。它补齐的是 P0 建模产品从：

**“我能把模型设计出来”**

走向：

**“团队敢把这个模型作为一个受控版本使用”**

之间缺失的治理层。

因此本轮主要映射：

- **F04 版本发布**：从“本地历史”向“正式版本 / 生效 / 回退”推进；
- **F19 语义权限与策略**：开始建立可信身份和最小授权；
- **F20 证据、追踪与审计**：建立变更、审核、发行、生效的可追溯链；
- **F25 协同建模与审查**：建立提交、审核、退回、拒绝；
- **F28 语义质量门禁**：把结构检查与正式发布资格分开。

**成熟度不能因为 UX-Low 完成而直接从“未实现”升为“基础可用”。** 当前只能记录为“产品设计已形成、真实功能未实现”。

## 7. 一条工业黄金故事：全局进度的校准尺

**问题**：QMS 检测到一批物料质量异常，质量工程师希望知道影响哪些订单，并有据可查。

| 过程 | 用户应该能操作的真实结果 | 目前距离 |

| 设计语义（P0） | 创建批次、质量事件、工单、订单对象和关系 | **同包对象/属性/关系及本地历史基础可用；跨包未实现** |
| 审查发布（P0） | 经过可信人员审查、发布受控版本 | **未实现** |
| 绑定来源（P1） | 将 QMS、MES、ERP 事实映射到对象及关系，显示来源 | **未实现** |

## 8. 以后如何把每个 PR 自动映射到全局功能

每个 PR 在描述中简要映射相关 F 编号、用户结果、变化性质、验证与未测项；普通修复不强制生成独立报告或重复大表。重要里程碑才更新本账相应行。**只补测试不能直接提高功能覆盖率；只能提高已有子项可靠性。** 不允许把样例/POC 算作正式产品。

维护职责：本文件是当前**功能总账**；[交付说明模板](./交付说明模板.md) 供重要里程碑按需使用；旧版交付/评审记录描述其历史基线。技术错误码和细目继续放在相应合同、测试和操作文档。最终产品定义权威仍是 V1.3 和通过评审的 OFIP。
