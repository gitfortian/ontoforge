## 1. 这轮到底完成了什么

上一轮 UX-Low 已经把模型治理的业务流程确定下来：

**模型变更 → 审核 → 正式版本 → 生效 → 回退**

本轮没有提前开发后端，而是把这条流程进一步做成了与 OntoForge 当前 Studio 视觉体系一致的**高保真、可操作产品原型**。

因此这轮完成的是：

> **产品交互目标定稿候选**

而不是：

> **模型治理真实功能完成。**

## 2. 本轮用户能看到的完整产品效果

### 模型包概览

进入模型包后，第一眼看到：

- 当前生效版本；
- 待处理变更；
- 正式版本数量；
- 当前需要本人处理的事项；
- 最近治理记录；
- 下一步动作。

用户不需要先理解 Snapshot、Digest、revision。

### 我的变更

可以看到：

- 哪些模型正在修改；
- 修改了什么；
- 当前处于草稿还是等待审核；
- 风险是什么；
- 下一步是什么。

点击“准备模型变更”后，从右侧抽屉完成提交。

### 待我审核

审核者看到：

- 提交人；
- 基线版本；
- 变化内容；
- 风险；
- 检查结果；
- 审核依据。

然后才出现：

**批准 / 退回修改 / 拒绝**

### 正式版本

明确区分：

**已发行**

和：

**当前生效**

用户不会因为看到 0.5.0 已发行，就误认为生产已经切换。

### 生效范围

明确展示：

**production-core**

当前：

**0.4.0**

目标：

**0.5.0**

并要求填写生效原因。

### 治理记录

形成：

**提交 → 审核 → 正式发行 → 生效 → 回退**

的完整时间线。

## 3. 本轮重点解决的产品问题

### 问题一：技术术语过多

一级产品界面现在主要使用：

- 模型包；
- 模型变更；
- 审核；
- 正式版本；
- 生效范围；
- 治理记录。

技术信息进入“查看技术定位信息”等二级区域。

### 问题二：正式版本和生效混淆

产品明确拆成：

**创建正式版本**

↓

**选择生效范围**

↓

**让指定范围生效**

### 问题三：异常状态没有行动指引

超时状态直接告诉用户：

> **不要重复点击。**

下一步：

> **核对当前生效版本。**

版本冲突、无权限、请求结果未知不使用同一个模糊错误状态。

### 问题四：回退语义不准确

不使用：

> 撤销发布

而使用：

> **切回历史版本**

并明确：

> 这不会删除历史正式版本，也不会撤销已经发生的 MES / ERP 业务操作。
