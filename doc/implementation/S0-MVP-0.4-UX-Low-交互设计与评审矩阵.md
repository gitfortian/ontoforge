>
> **原型**：[ofip-0004-linktype-lowfi.html](../prototypes/ofip-0004-linktype-lowfi.html)。查看 GitHub 源码后可下载 HTML 在本机浏览器打开；无需 npm、Docker、数据库或账号。

> **复验脚本**：[ofip-0004-lowfi-state-check.mjs](../prototypes/tests/ofip-0004-lowfi-state-check.mjs)，可在仓库根目录运行 `node doc/prototypes/tests/ofip-0004-lowfi-state-check.mjs`。它通过 Node 内置 VM+模拟 DOM 检验原型状态合同，**不是 Chromium/真实用户界面端到端测试**。

> **内容边界**：所有“保存/检查/冻结/差异/冲突”都为 Mock 内存模拟，刷新即清空，不包含真实数据库、不可变快照、可信摘要或发布；导入示例数据不代表接入 QMS/MES/ERP，也不是工业关系实例。

## 1. 用户是谁、这一轮解决什么问题

用户：工业领域架构师、制造质量建模人员。他们需要从单对象编辑自然扩展到批次、工单、订单的**关系定义**，不被多个菜单和技术工具打断，也不能因为切换对象、删除对象或异常重试而丢失模型资产。

**原型设计目的**：在正式写代码之前，检验「一处工作台能否完成多对象和关系的整条业务操作链」，并识别用户卡点。它对应全局 F02 本体建模、F03 校验、F04 本地版本子项、F05 模型包、F28 语义质量门禁；**这些功能的新增关系子项依然尚未实现为产品**。

## 2. 信息架构与页面布局

```text
左侧原有导航：本体设计 > 模型包 > 当前模型包
  当前工作台（一个页面，不新建“专业工具”一级菜单）
   ├─ 对象类型 Tab  → 对象列表 / 对象详情 / 属性 / 主键 / 新增和删除
   ├─ 关系类型 Tab  → 关系列表 / 源对象 / 目标对象 / 基数 / 证据要求
   ├─ 保存与检查 Tab → 保存进度 / 检查修订 / 逐条问题定位 / 异常恢复
   └─ 历史与对比 Tab → 本地历史列表 / 选择 From-To / 结构风险
  始终可见的底部操作栏：保存编辑进度 → 检查完整性 → 留存本地历史
```

**为什么这么设计**：专业建模过程的工作对象是“一个包”，不是“类型管理页面”“关系引擎页面”“快照工具页面”互相跳转。当前原型用简洁表单/列表，不先引入复杂关系图编辑器；后续高保真可以增加只读关系概览，但不改变语义权威。

**主要文案约束**：默认展示“关系类型/来源对象/目标对象/一对多/保存/检查/历史”，技术 id、apiName 和摘要放在可理解的业务标签下。页面始终提示：**只是模型定义，暂无实际业务对象关系；本地历史不是正式发布。**

## 3. 低保真黄金故事：用户可逐步验证

1. 打开原型，初始有生产批次一个对象。点击**载入制造示例**，出现「生产批次、生产工单、销售订单」三个对象和两条关系；这一步仍是**未保存的本地编辑**。
2. 在「对象类型」里切换查看不同对象的标识、属性和主键；点击**新增对象**，新增一条待填写模型定义，不会偷偷丢掉其他对象。
3. 进入「关系类型」，查看「生产批次归属工单（多对一）」和「工单关联销售订单（多对多）」。新增关系时按顺序选择来源和目标，选择中文解释的基数及未来是否要求证据。
4. 点击**保存编辑进度**。修订号增加，旧校验失效；点击**检查模型完整性**，三个对象、两条完整关系应显示 `VALID`。关系没填完时可以保存，但应是 `INCOMPLETE`。
5. 点击**留存本地历史版本**，第一份历史保留当前全部模型对象和关系；修改其中一条关系的基数，再保存、校验、留存第二份历史。
6. 进入**历史与对比**，选择 From/To 两版，看到关系变更的位置和“潜在破坏”等提示；如果把 evidenceRequired 从 true 改成 false，应提示“需治理复核”。
7. 通过**重置原型**清空 Mock 状态，或刷新页面看到临时模拟数据消失；不能误当成真实产品持久化。

**关键异常路径**：删除被关系引用的工单，会留下带错误的关系定义而非自动级联删除；另一标签页提交后本地再次保存显示冲突并保留本地内容；保存/冻结回执未知时必须先核对结果，避免盲目重复提交。

## 4. UX-Low 交互规则（冻结候选）

| 页面/动作 | 主要决策 | 用户体验与异常提示 | 后续高保真重点 |
| --- | --- | --- | --- |
| 进入模型包 | 直接进入当前建模工作台，Tab 而非多级菜单 | 顶部提示未发布、修订和未保存状态 | 同一项目 UI 规范和导航语义 |
| 对象列表 | 左侧对象选择、右侧编辑，避免整个页面来回跳 | 新增对象保留完整包；切换 Tab 不丢修改 | 多对象查找、密度和删除确认 |
| 对象 ID 修改 | 稳定 ID 为身份权威，改 label 不破坏关系 | 改 ID 后原关系提示悬空，不自动“帮改” | 更明确的结构变更影响确认 |
| 删除被引用对象 | 显示影响的关系数量，关系不自动删除 | 允许保存未完整 WIP；INVALID 阻止留存 | 风险分层与一键跳到受影响关系 |
| 关系编辑 | 来源→目标，中文基数释义，明确证据要求 | 端点必须来自同包对象，未选择可暂存 | 端点选择器与主次视觉顺序 |
| 保存 | 保留修订比较与全部 EditorDoc | 成功刷新校验状态；并发 409 保留全部本地内容 | 底部固定工具栏与轻量保存反馈 |
| 检查 | 只检查已保存且最新的修订 | 缺失 INCOMPLETE，错误 INVALID，可点击跳到对应关系 | 问题分组和自动定位 |
| 留存历史 | 必须保存且 `VALID` 同修订 | 非发布，本地历史只读；重复同修订不制造第二份 | 冻结确认弹窗及结果找回 |
| 关系差异 | 以关系稳定 ID 比较 | 新增/删除、端点/基数变化、证据放宽风险 | 业务文案替代纯 JSON Path |
| 保存/冻结未知 | 结果未知不算成功 | 用服务器内容或同一幂等请求找回 | 恢复入口、反馈与返回路径 |

## 6. 审核发现和需要高保真进一步处理的问题

| 优先级 | 发现 | 建议修订 |
| --- | --- | --- |
| P0 | 用户容易混淆“关系定义”与“实际对象关系” | 在所有关系页面保留“只定义类型、无真实实例”解释，历史也标本地只读 |
| P0 | 删除被引用对象后如果自动级联，会破坏语义资产 | 当前原型采用“删除对象→留下悬空关系→人工定位修复”，高保真需突出影响数量 |
| P0 | 多标签/网络异常可能发生误保存 | 全包 dirty、保存冲突和未知结果核对入口必须清楚可见 |
| P1 | 当前原型对象属性仅提供简化版输入，非完整专业字段表单 | 高保真需恢复全部 Native V0.2 可编辑属性类型、枚举、数据分类等，不能因原型简化而削弱 0.2 能力 |
| P1 | 保存、校验、历史三个 Tab/入口可能让人重复判断下一步 | 继续采用固定底部流程，并将“当前状态/下一步”提示提升 |
| P1 | 错误报告仍显示技术 JSON Pointer | 高保真优先展示“生产工单 → 关联关系 → 目标对象”，详细路径可折叠 |
| P1 | 原型中的版本记录只有内存递增序号 | 高保真必须区分真实历史创建时间/来源修订；不得沿用原型序号当生产发布标识 |
