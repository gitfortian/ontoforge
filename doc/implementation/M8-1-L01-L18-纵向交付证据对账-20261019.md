## 1. 范围与产品交付边界

用户故事：Native 定义并冻结两端 ObjectType / LinkType → M5 保存同一个 Snapshot 的 SOURCE/TARGET Data Binding revision → 进入原 M7 ObjectSet 工作台的 M8.1 单列 FK 配置 → 真实双端 FULL 校验 → 保存不可变 LinkBinding revision → 按 ObjectRef 或有界根集合执行 OUT/IN **一跳** → 查看关联事实、质量、预算、签名分页和错误恢复。

- **属于 M8.1**：同源单列 FOREIGN_KEY、ONE_TO_ONE/ONE_TO_MANY/MANY_TO_ONE、两端独立 identityDomainId、当前权威主键、Linked ObjectRef、COUNT_DISTINCT/SUM、B0 当前授权和每页回查、受控 PostgreSQL 17、V10 元数据迁移。
- **不属于 M8.1**：桥表 MANY_TO_MANY、两跳/无界图遍历、SQL 自定义、外部 Action、全量物化 LinkFact、生产 CDC、正式版本发布。
- **主线共存**：保留 Yak 账号/Session **Flyway V8**、工作空间 **V9**；M8.1 不重写历史迁移，新增 **V10**。工作空间 `scopePackages` 限制同时覆盖 M7 与嵌入式 M8.1。

## 3. 真实测试级别与数据一致性边界

1. **质量通过不等于发布**。在本次验收台账最后更新前，真实代码 HEAD `c5d36b63d524621aa792661c48165eb4b5d76bc4` 的三组 Actions 已 `completed/success`：[S0](https://github.com/gitfortian/ontoforge/actions/runs/39242548518)、[Docs](https://github.com/gitfortian/ontoforge/actions/runs/39242548654)、[Required Quality](https://github.com/gitfortian/ontoforge/actions/runs/39242548599)；涵盖并发准入及 L03 新增 HTTP/PG17 反例。**本台账文档变更自身会形成更新的 HEAD，必须重新核对最终三组 CI 后才能签收**。
2. **并发与缓存范围**：事务内原子检查的是已冻结 JSON **16 MiB / 32 slots**；本轮再加最多 **4 个并行在建查询**的 fail-fast 全局 Semaphore 准入。仍未直接衡量 JDBC 行对象、构建中 JsonNode、JVM 堆和 GC 峰值；生产级硬内存 SLA 仍需 heap profile 和资源配置验收，不能使用“已消灭 OOM”表述。
3. **来源一致性**：M8 从白名单 PostgreSQL 同一只读 REPEATABLE_READ 事务读 SOURCE/TARGET；它与元数据写入事务并非同一个外部事实事务，`sourceReadRefs` 和结构指纹保留此边界。
4. **EXPLAIN 证据**：9,802 个关联的 PG 计划验证 SQL 查询，不代表端到端 Java Join 在所有硬件/并发下始终小于 3s；服务端真实请求包含 deadline 检查和 429/503 fail-closed。
5. **Windows 11 用户本机 PostgreSQL UAT：NOT RUN**。CI 的 Windows PowerShell 5.1 parser 只能证明脚本语法，不能替代本机数据库、账号 Session、Source grant、Flyway V10 真实升级验证。
