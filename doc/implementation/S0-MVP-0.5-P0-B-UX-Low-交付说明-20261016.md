## 1. 这轮到底解决了什么

上一轮我们已经确定了“模型变更 → 审核 → 正式版本 → 生效 → 回退”的业务规则，但仍存在一个产品问题：

> 研发知道 ChangeSet、ReviewDecision、SchemaRelease、Activation 是什么，普通用户却不应该被迫理解这些技术对象才能完成工作。

所以本轮把技术合同翻译成了用户真正能理解的产品流程。

用户看到的不是：

> 创建 ChangeSet → 提交 ReviewDecision → 生成 SchemaRelease → 创建 ActivationEvent

而是：

> **准备模型变更 → 提交审核 → 审核通过 → 创建正式版本 → 让指定范围生效 → 出问题时切回历史版本**

这是本轮最重要的产品设计成果。

## 4. 目前用户最终能做到什么

如果未来按照本轮设计实现完成，一个模型设计者可以：

**① 打开模型包**

看到：

> 当前生效版本：0.4.0

而不是看到一堆 Snapshot ID。

**② 修改模型**

例如：

> 批次 → 工单：MANY_TO_ONE → ONE_TO_MANY

然后看到：

> 潜在破坏性变化，需要领域审核。

**③ 提交变更**

填写：

> 为什么要修改这个模型？

提交后明确提示：

> **这份变更内容已经固定。之后继续修改模型不会改变正在审核的内容。**

**④ 审核**

审核人看到：

- 原来是什么；
- 现在是什么；
- 为什么修改；
- 有什么风险；
- 质量检查是否通过；
- 当前消费者影响是否未知。

然后才决定：

> 批准 / 退回修改 / 拒绝

**⑤ 创建正式版本**

看到：

> 0.5.0 已经经过审核，可以创建正式版本。

同时明确：

> **创建正式版本不会自动让生产范围使用它。**

**⑥ 让指定范围生效**

例如：

> production-core  
> 当前：0.4.0  
> 切换：0.5.0

用户确认后才切换。

**⑦ 出现问题**

选择：

> 切回历史版本 0.4.0

系统留下新的治理记录。

## 5. 本轮特别解决的三个产品误区

### 误区一：保存就是发布

不是。

**保存模型 → 本地快照 → 提交审核 → 正式版本 → 生效**

是不同阶段。

### 误区二：正式版本就是正在使用的版本

不是。

一个版本可以：

> 已正式发行，但还没有任何业务范围使用。

所以产品必须分别展示：

**正式版本**

和

**当前生效版本**。

### 误区三：回退就是删除新版本

不是。

0.5.0 发布以后，即使切回 0.4.0：

> 0.5.0 仍然存在。

只是当前生效指针从：

> 0.5.0 → 0.4.0

并留下新的回退记录。

## 10. 产品负责人一眼看懂

> **这轮不是“开发了审批功能”。**

真正完成的是：

> **把“模型治理”从一组技术概念，变成了一条普通用户能理解的产品工作流。**

现在砺元的产品主线已经可以清楚地表达为：

**设计模型 → 保存模型 → 留存历史 → 提交变更 → 审核变更 → 创建正式版本 → 选择生效范围 → 追踪 → 安全回退**

而当前真正做到的边界仍然是：

**设计模型 + 保存 + 校验 + 历史 + Diff + 关系建模基础。**

**“审核 → 正式版本 → 生效 → 回退”目前完成的是产品设计和技术合同，还没有完成真实产品功能。**
