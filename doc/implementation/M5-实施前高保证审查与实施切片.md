# M5 通用 Data Binding 实施前高保证审查

**审查日期：** 2026-10-18  
**审查基线：** `main`，包含 M4 Runtime Type Catalog（PR #56）、M5 UX-Low（PR #60）与 UX-High（PR #61）  
**审查类型：** 实施准备度 / 安全边界 / API 与数据合同 / 验收策略  
**结论：** 原型阶段已通过；生产实现仍为 **Not Started**。本文为实施前审查，不构成 OFIP-0007 的维护者投票。

## 1. 结论摘要

UX-Low 与 UX-High 已完成评审并合并，M5 的用户主线已明确：

> 选择已保存 Local Snapshot 与自定义 ObjectType → 发现受控 PostgreSQL 来源 → 配置来源键和属性映射 → 查看原始样本与映射对象 → 执行有界校验 → 保存不可变 revision → 从绑定目录重开当前或历史版本。

在进入生产代码前，仍有四项必须明确的实现边界：

1. **现有固定绑定不能复用为通用绑定存储。** `QualityMvpController` 面向制造质量追溯，使用固定十项 Mapping 与 `mvp_demo_binding`；其 upsert 会覆盖同一 package 的映射，不满足按 ObjectType 唯一、revision 不可变的合同。
2. **M5 需要真正独立的只读来源连接。** 当前 `application.yml` 只配置应用主 DataSource；现有来源发现与样本查询使用主 `JdbcTemplate`。把查询标成 read-only 或在 Java 中隐藏写按钮，都不能证明 PostgreSQL 账号没有写权限。
3. **安全路由与 UI 路由尚未接入 M5。** 两套 SecurityFilterChain 都没有 M5 的 `/api/runtime/**` 路径；`main.tsx` 也没有绑定目录路由，M4 Runtime Type Catalog 当前没有“从快照类型创建绑定”的产品入口。
4. **提案合同需补齐绑定目录查询和摘要算法。** UX-High 已有绑定目录、历史 revision 查看与重开，但 OFIP-0007 的 Public Interfaces 尚未定义目录列表 API；`digest` 与 `sourceSchemaFingerprint` 也需要固定可重复计算的 profile。

因此，下一步应先把这些合同缺口写回 OFIP-0007 并进行维护者显式决策。**本 PR 不包含 Java/React/Flyway 生产实现。**

## 2. AS-IS 代码证据

### 2.1 可复用能力

| 现有能力 | 实际证据 | M5 应如何复用 |
| --- | --- | --- |
| Native 类型目录 | `RuntimeTypeController` 提供 draft/snapshot 类型目录与详情；`RuntimeTypeResolver` 返回 packageId、ObjectType/Property 合同和快照摘要 | 复用服务端 resolver，不从前端传入的 label、类型字符串或客户端 PASS 构建类型合同 |
| 快照完整性 | `NativeSnapshotService.get(UUID)` 校验规范化字节、SHA-256、JSONB 镜像、Native Schema 与 package identity | 绑定保存前重新解析指定 snapshotId，并核对其 payloadSha256 |
| 既有包授权 | `B0AuthorizationService` 已有 READ_DRAFT / WRITE_DRAFT / READ_SNAPSHOT 等操作 | M5 复用现有包/快照授权，不另造角色或身份系统 |
| 本机 MVP 安全模式 | `LocalMvpSecurityConfig` 校验 loopback server 与允许的本机数据库名 | 保留显式 `mvp-local` 模式；对新增来源连接也必须增加独立隔离检查 |
| 真实 PG 集成测试 | `IsolatedPostgresTestDatabase` 要求测试数据库位于 loopback 且数据库名匹配 `ontoforge_test_*` | M5 测试继续使用隔离 PostgreSQL；来源只读角色需要单独证明权限 |

### 2.2 不可直接复用为 M5 的能力

- `QualityMvpController.sourcesInternal()` 只接受 `text / character varying / character / uuid / integer / bigint` 等既有追溯场景类型，不能覆盖 M5 的 DECIMAL、BOOLEAN、DATETIME、ENUM 类型兼容矩阵。
- 该控制器通过主 `JdbcTemplate` 读取来源样本；`/bind` 将单条 `mvp_demo_binding(package_id,draft_id,bound_revision,source_map)` 以 `ON CONFLICT(package_id) DO UPDATE` 覆盖更新。它是固定追溯场景的可变绑定，不是通用 Binding revision 历史。
- V4 的 `mvp_source_orders / mvp_source_work_orders / mvp_source_batches` 和 V6 的 `demo_impact_*` 是现有合成质量追溯夹具，不是 M5 的 Supplier 类型夹具。
- 现有 `main.tsx` 只分发 Native 模型、Runtime Type Catalog 与质量追溯路由；没有 `DataBindingWorkspace` 或绑定目录路由。
- 现有 `SecurityConfig` 只允许已知的 `/api/model/**` 与 `/api/mvp/quality/**` 等路径，其他路径 fail-closed；`LocalMvpSecurityConfig` 也未登记 M5 路径。

## 3. 必须先补齐的合同缺口

### H1. 绑定目录 API（阻塞 UX-High 落地）

UX-High 的目录需要列出当前绑定、ObjectType、来源、revision、最后校验状态，并能打开详情或创建新版本；当前 OFIP-0007 只定义了创建、更新、单条详情，没有列表接口。

建议新增：

`GET /api/runtime/bindings?packageId=...`

只返回该 package 每个 ObjectType 的当前 head 摘要；响应字段至少包括 `bindingId`、`objectTypeId`、`currentRevision`、`sourceId/schema/table`、`validationStatus`、`checkedAt`、`checkedRows`。按稳定 ObjectType ID 排序。历史版本仍通过 `GET /api/runtime/bindings/{id}?revision=n` 读取。该端点必须执行服务端 package 授权，不能接受客户端角色声明。

### H2. 摘要与来源结构指纹 profile

目前提案要求 `digest` 与 `sourceSchemaFingerprint`，但尚未完全固定可重复算法。建议在合同中明确：

- Binding revision digest：`JCS RFC 8785 + SHA-256`，profile 标识 `jcs-rfc8785-v1`，输出裸小写 64 位 hex。输入为该 revision 的版本化合同字段和验证摘要，排除 digest 自身及纯响应展示字段；validation 不得反向包含此 digest，避免循环。
- Source schema fingerprint：profile 标识 `pg-source-schema-v1`，对 schema/table、按 ordinal 排序的列名、精确 PostgreSQL type/udt_name、nullability、primary/unique key 约束构成规范化 JSON，再使用同一 JCS/SHA-256 规则。不能把来源行值或抽样内容放入 fingerprint。
- 每次 preview 和保存前重新计算来源 fingerprint；不一致返回 `409 BINDING_SCHEMA_DRIFT`，不得按同名列自动重绑。

### H3. 应用 DataSource 与来源只读 DataSource 必须分离

`application.yml` 当前只有主 `spring.datasource`。M5 必须新增服务端配置的来源别名（首版仅 `local-pg-sandbox`），并建立独立的 source `DataSource/JdbcTemplate`：

- 客户端只能提交 `sourceId`、schema/table/column 标识；不能提交 JDBC URL、主机、用户名或密码。
- 主 DataSource 只负责 Native 元数据与 Binding revision 写入；source DataSource 只负责目录、样本与校验读取。
- 来源数据库账号必须在 PostgreSQL 层真实只有允许表的 SELECT 权限；`readOnly=true` 仅是额外防护，不是权限证明。
- `mvp-local` 启动校验必须同时验证来源 JDBC URL 为 loopback、数据库名属于允许的本机 `ontoforge` / `ontoforge_test_*` 范围，并拒绝 URL 内嵌凭据或 JDBC options。
- 测试必须尝试 INSERT/UPDATE/DDL，并断言来源角色被 PostgreSQL 拒绝；不能用应用层返回 403 代替数据库权限证据。

### H4. 路由与入口合同

生产实现需同时接入：

- JWT 模式：在 `SecurityConfig` 中精确加入 M5 所需 HTTP 路径并要求 authenticated；不得添加宽泛的 `/api/** permitAll`。
- 本机模式：在 `LocalMvpSecurityConfig` 中仅为 M5 精确路径添加本机可用规则，继续依赖 loopback 和隔离数据库守卫。
- 前端：在 `main.tsx` 加入绑定目录路由和菜单入口；在 `RuntimeTypeWorkspace` 的 Local Snapshot 类型详情增加“创建绑定”入口，传递 snapshotId 与 ObjectType ID。Validated Draft 可用于预览，但持久绑定首版只能选择 Local Snapshot；从 Draft 进入时应引导先冻结快照，而不是静默转成快照。

## 4. 建议的持久化模型与事务边界

V1–V6 已存在；**下一版新迁移为 V7**，不得修改历史 Flyway migration，也不得复用 `mvp_demo_binding` 存通用绑定。

建议分为三类数据：

1. `runtime_binding`：稳定身份（bindingId、packageId、objectTypeId、identityDomainId、createdAt）；约束 `UNIQUE(packageId, objectTypeId)`，保证同一类型只有一条当前绑定身份。
2. `runtime_binding_revision`：不可变版本表，主键 `(bindingId, revision)`，保存精确 Local Snapshot、payloadSha256、sourceId/schema/table、sourceSchemaFingerprint、sourceKey、fieldMappings、digest、validation 与创建时间。
3. `runtime_binding_head`：每个 bindingId 一条当前指针，指向某个已存在 revision；所有 revision 与 head 更新在同一事务中完成。

更新流程必须用 expectedRevision 做 CAS：锁定/读取 head，核对 expectedRevision，重新校验快照、来源结构与类型映射，写入新 revision，再原子更新 head。并发更新只能一个成功；冲突返回 `409 BINDING_REVISION_CONFLICT`，不覆盖历史版本、不丢本地编辑。若采用其他表结构，必须保持同等唯一性、不可变性和原子性。

## 5. 单个纵向实施 PR 的验收矩阵

| 层次 | 必须覆盖 | 通过证据 |
| --- | --- | --- |
| Contract / Schema | 新增版本化 `local-binding-v1` schema；未知字段、错误类型、未支持映射被拒绝 | Schema 测试、错误码测试 |
| Native 引用 | snapshotId、packageId、ObjectType/Property ID、payloadSha256 由服务端解析并核验 | 跨包拒绝、快照摘要损坏拒绝、草稿变更不改变已绑定引用 |
| 来源目录 | 只允许配置来源别名、public 白名单 BASE TABLE、受支持 PG 类型 | 非白名单表、view、未知类型拒绝；目录截断有显式标记 |
| 类型映射 | STRING / INTEGER / DECIMAL / BOOLEAN / DATETIME / ENUM 的兼容矩阵；主键映射 primaryKeyRef；非键至少两个属性 | 兼容/不兼容边界测试；不做隐式转换 |
| Preview / Validate | 样本最多 20 行；全量校验最多 10,000 行或 3 秒；检测空键、重复键与冲突、必填属性 | 真实 PG HTTP 测试；超预算不是 PASS；冲突不泄露源行值 |
| 持久化 | 创建、更新、列表、详情、历史 revision 重开、digest 重算 | 真实 PG17 migration/integration tests |
| 并发 | 相同 ObjectType 并发创建、相同 expectedRevision 并发更新 | 唯一约束与 CAS 竞争测试；只允许一个 head 更新成功 |
| 只读权限 | 来源账号无 INSERT/UPDATE/DELETE/DDL 权限 | PostgreSQL 真实拒绝证据，不只测 HTTP 层 |
| 安全路由 | JWT 401/403、package/snapshot ACL、mvp-local loopback/source URL 守卫 | Spring Security 集成测试；无 token 不可访问生产路径 |
| React / Chromium | 从 M4 类型详情进入、目录列表、映射双预览、保存重开、历史版、漂移/不可用/预算/CAS 错误、窄屏与未保存确认 | 专用 Chromium suite + React production build |
| 回归 | 既有 `QualityImpactObjectSetTest`、M4 RuntimeTypeTest、NativeSnapshotTest 与所有质量门禁保持通过 | Required Quality / Architecture Docs / S0 PG 门禁全 PASS |

## 6. 单 PR 的建议实施顺序

一个纵向 PR 完成用户可见闭环，不按 controller、repository、单表或单测试拆成多个半成品 PR：

1. V7 迁移 + 新 typed Supplier 测试夹具 + 真实来源只读角色配置/守卫。
2. Binding DTO/Schema、Source Catalog、Typed Mapping/Validation、不可变 revision store 与 CAS。
3. 精确 API 路由和授权、列表/创建/更新/详情历史接口。
4. React 绑定目录与五步工作台，接入 M4 Snapshot Type 入口。
5. 真实 PG17 集成测试、权限负向测试、并发与漂移测试、Chromium 用户故事回归。
6. 完整 review、运行全部 Required Quality/Architecture/S0 gates，并附功能完成说明、风险和下一步。

不提前实现 M6 Object Runtime、M7 ObjectSet、Action 写回、生产连接器或 Agent；不把当前质量追溯的固定 Mapping 改造成隐式通用 DSL。
