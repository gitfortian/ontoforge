# OntoForge · 砺元 S0 工程模块规划与命名规范

> 适用：ontoforge 当前 S0-MVP 与后续 P0–P4。规划依据：[总体架构 V1.3](../本体产品总体功能与技术架构设计_v1.3.md)；工程规范参考：[Yak Ops 根 POM](https://github.com/weifuwan/yak-ops/blob/main/pom.xml)、[Yak Ops Boot](https://github.com/weifuwan/yak-ops/tree/main/yak-ops-boot)、[Yak Ops UI](https://github.com/weifuwan/yak-ops/tree/main/yak-ops-ui)。
>
> **原则：工程模块规划完整；真实模块按可验收 MVP 分阶段创建。当前没有相关功能的模块，只能出现在本规划表中，不得创建空壳项目或伪数据页面。**

## 1. Yak Ops 的可复用工程规则

已核对 Yak Ops 实际仓库：根目录 `pom.xml` 为 Maven 多模块 Parent/Reactor；模块按 `yak-ops-boot`、`yak-ops-common`、`yak-ops-platform`、`yak-ops-dao`、`yak-ops-core`、`yak-ops-business`、`yak-ops-spi`、`yak-ops-plugins`、`yak-ops-ui` 等业务前缀和职责命名；Boot 入口位于 `io.yak.ops.boot`。

本项目使用等价的统一前缀 `ontoforge-`，Java GroupId `io.ontoforge`，包名按职责分为 `io.ontoforge.boot`、未来 `io.ontoforge.core` 等。

**重要区别**：Yak Ops 的 `yak-ops-ui` 内部目前还有多应用工作区 `apps/web`。本项目 S0 只有一个独立 React 前端，直接把 `ontoforge-ui` 作为 npm 工程根目录；不引入多应用 Workspace，避免继续存在你不认可的 `apps/api` / `apps/web` 临时工程结构。未来确实出现第二个前端应用或共享包时，再单独评审 Workspace。

## 2. 已落地工程模块（S0 仅三个）

| 单元 | 实际路径 | 职责 | 当前实现 |
|---|---|---|---|
| Maven Parent/Reactor | `/pom.xml`，artifactId=`ontoforge` | 唯一统一版本、Java 21、Spring Boot BOM、真实 Maven 模块列表 | 只注册 `ontoforge-boot` |
| 应用启动模块 | `/ontoforge-boot/`，artifactId=`ontoforge-boot` | Spring Boot 入口、HTTP API、当前最简 JDBC/Flyway 和基础测试 | 只有状态接口，**无登录/权限/工作空间** |
| 前端工程 | `/ontoforge-ui/`，npm name=`ontoforge-ui` | React/Vite/TypeScript、基础系统概览 | 只真实读取后端运行状态 |

配套本地 PostgreSQL Compose 放置在仓库根 `compose.yaml`，符合 Yak Ops 根目录运维文件习惯。根目录 `README.md` 是唯一的 MVP 本地启动入口。工程目录不能再用 `apps/api`、`apps/web` 或 `infra/compose.dev.yml`。

Java 应用类 `io.ontoforge.boot.OntoForgeApplication`；Controller `io.ontoforge.boot.controller.SystemStatusController`。**原 HTTP 合同 GET /api/system/status、PostgreSQL V1 的持久 UUID、前端页面、端口和本机开发限制保持不变。**

## 3. 完整模块规划：未来按真实业务出现才建工程

| 规划模块 | 与 Yak Ops 对应的规范 | 本体产品职责 | 创建触发门禁 |
|---|---|---|---|
| `ontoforge-common` | yak-ops-common | 多模块共同依赖的最小公共值对象和错误类型 | 至少两个已存在模块确有复用需求 |
| `ontoforge-platform` | yak-ops-platform | 认证、权限、工作空间、Policy 与平台公共治理 | 真实多用户或需要访问真实企业数据时，经过独立安全评审 |
| `ontoforge-dao` | yak-ops-dao | PostgreSQL 持久化、Flyway、Repository 适配 | P0 Native 模型持久化超出 Boot 最小能力时 |
| `ontoforge-core` | yak-ops-core | Native Type/Link、DSL/AST、Compiler、Registry 核心合同 | P0-A 首个真正的建模/校验闭环 |
| `ontoforge-business` | yak-ops-business | ChangeSet、Review、Release、业务用例编排 | 业务用例有跨领域/持久化依赖时 |
| `ontoforge-spi` | yak-ops-spi | Connector、ObjectSet 执行器和外部 Action 扩展 Port | P1 真实外部数据接入 |
| `ontoforge-plugins` | yak-ops-plugins | 具体 ERP/MES/QMS 与外部查询适配器 | P1/P3 有实际插件接口及业务需求 |
| `ontoforge-test-utils` | yak-ops-test-utils | 通用集成测试夹具 | 两个实际模块的测试逻辑需要共享 |
| `ontoforge-e2e` | yak-ops-e2e | 多页面/跨模块黄金故事自动化验收 | 真正具备可端到端操作的 P0 用户故事 |
| `ontoforge-dist` | yak-ops-dist | 正式打包、部署与交付分发 | 可部署企业环境的发行版开始建设时 |
| `ontoforge-bom` | yak-ops-bom | 外部依赖的跨模块版本约束 | 模块化依赖复杂到需要单独 BOM 时 |

**不推荐**为了“看起来像 Yak Ops”直接复制其 yak-flow、任务执行、调度、CDC 或全部业务模块。可复制的具体第三方代码必须在 PR 中单独做许可证及安全审查；本轮仅借鉴其**工程结构和命名规则**，不复制它的业务实现。

## 4. 模块依赖纪律

- `boot` 是组装层，不是长期承载全部领域逻辑的“大杂烩”。S0 临时将最简 Flyway 与状态查询留在 boot，是为避免创建没有可验证功能的 dao/platform/core 空模块；后续产生第一个真实业务持久化需求再迁移。
- `core` 定义 Native Ontology 的领域概念与约束，不得反向依赖 `boot`、具体 Connector 或前端。
- `business` 实现用例并依赖受控领域接口；`dao` 和 `plugins` 是技术实现，不允许外部源系统直接决定本体模型 API。
- `platform` 的用户、权限、工作空间属于独立开发与安全 Gate，未建设之前前端占位不能对外宣称提供鉴权。
- 将来每创建一个新 Java 模块，需根 Maven Reactor 正式注册、明确依赖方向、实际测试与用户任务，禁止无用的通用 DTO/接口框架。
- 项目外部发布版本由总体架构 V1.3、合同 Native V0.2、各实施版本独立管理。勿将文档版本与 `pom.xml` 软件版本混淆。

## 5. 本次纯结构重构验收

本次 PR 不新增业务功能，不改 PostgreSQL 表或 Flyway 版本，不引入用户/权限，也不实现 Native 建模。验收顺序：

1. 根目录 `docker compose up -d`，仍只监听本地 PostgreSQL。
2. 根目录 `mvn -pl ontoforge-boot spring-boot:run`，Spring Boot 正常启动，保持 **http://127.0.0.1:8080/api/system/status**。
3. `cd ontoforge-ui` 后执行 `npm install && npm run dev`，打开 **http://127.0.0.1:5173**，看到原 S0-MVP 页面。
4. 既有 PostgreSQL 数据卷和 `platform_installation` 安装 UUID 保持不变。不能为了改名要求删除本机数据。
5. CI 必须执行根 Reactor 的实际 PostgreSQL/Flyway 测试及独立 UI TypeScript/Vite 构建，并拒绝仓库根临时 `apps`/`infra` 工程目录。
6. 新功能版本必须另行批准和验收；本次完成后 S0-MVP 的能力边界完全不变。
