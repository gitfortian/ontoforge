# OFIP-0005 P0-B · UX-Low 交互设计与评审矩阵

> **阶段：UX-Low / Design Review。** 本文件与 `doc/prototypes/ofip-0005-governance-lowfi.html` 配套。原型是浏览器内存 Mock，不是 React 产品功能；所有真实认证、权限、审核、发行、激活均 **NOT IMPLEMENTED**。

## 一、产品层目标

本轮不研究“API 怎么调用”，只回答用户最关心的六件事：

1. **我现在的模型是什么版本？**
2. **我改了什么，为什么要改？**
3. **谁需要审核？审核人到底看什么？**
4. **什么时候才算正式版本？**
5. **正式版本在哪里生效？**
6. **如果出问题，怎么安全回到以前的版本？**

因此界面统一使用：**模型包、模型变更、审核、正式版本、生效范围、治理记录**；技术摘要只在详情层出现，不把 Digest、CAS、JCS 等作为一级产品入口。

## 二、信息架构

```text
模型治理
└── manufacturing.production
    ├── 模型包概览
    │   └── 当前生效版本 / 最近变更 / 待处理事项
    ├── 我的变更
    │   └── 准备提交 → 待审核 → 已通过/已拒绝
    ├── 待我审核
    │   └── 变更列表 → 变更详情 → 批准/退回/拒绝
    ├── 正式版本
    │   └── 已发行版本 → 创建正式版本
    ├── 生效范围
    │   └── 当前版本 → 选择正式版本 → 确认生效
    └── 治理记录
        └── 提出 → 检查 → 审核 → 发行 → 生效 → 回退
```

**原则：不增加“治理中心”“版本中心”等孤立专业菜单。** 治理能力围绕模型包工作台自然出现。

## 三、黄金故事

### G1：设计者提交一项模型变更

```模型包 → 我的变更 → 准备提交变更
→ 选择当前版本作为基线
→ 选择已检查通过的模型快照
→ 填写业务原因
→ 明确知道“提交后内容固定”
→ 提交审核
```

**关键体验**：用户不用理解 ChangeSet。页面告诉他“这是一份固定的模型变更申请”。

### G2：领域审核者做决定

```待我审核 → CS-102
→ 看原版本/候选版本
→ 看具体变化
→ 看风险提示
→ 看质量检查
→ 看变更原因
→ 批准 / 退回修改 / 拒绝
```

审核页必须先回答“**改了什么**”，再回答“**有什么风险**”，最后才出现“**我怎么决定**”。

### G3：发行管理员创建正式版本

```正式版本 → 创建 0.5.0
→ 核对模型包 / 版本 / 来源变更 / 内容摘要 / 审核结论
→ 创建正式版本
→ 明确提示：正式版本 ≠ 当前生效版本
```

**绝不能出现**“发布后自动生效”这种含混语义。

### G4：激活管理员让指定范围使用新版本

```生效范围 → production-core
→ 当前 0.4.0
→ 选择 0.5.0
→ 查看从旧版到新版
→ 填写生效原因
→ 确认生效
```

如果同时有人切换过版本，用户看到的是“当前版本已经变化，请刷新”，而不是静默覆盖。

### G5：网络超时后的恢复

```操作完成但响应中断
→ 不重复点击
→ 查询原请求
→ 查看当前真实状态
→ 再决定下一步
```

产品文案不出现“系统可能已经成功/失败”这种无法行动的描述，要告诉用户**下一步去哪里确认**。

### G6：新版本不合适时回退

```
治理记录 / 生效范围
→ 选择历史正式版本 0.4.0
→ 查看 0.5.0 → 0.4.0
→ 填写回退原因
→ 创建新的生效记录
```

必须明确：**回退的是模型当前生效版本，不是撤销已经发生的 MES/ERP 业务操作。**

## 四、UX-Low 评审矩阵

| 编号 | 用户场景 | 必须看懂/完成 | 设计要求 | 当前原型 |
|---|---|---|---|---|
| UX01 | 查看模型包 | 当前生效版本、待处理事项 | 首页先给业务状态，不先给技术 ID | PASS |
| UX02 | 查看我的变更 | 哪些正在等审核 | 变更以“改了什么”命名 | PASS |
| UX03 | 创建变更 | 基线、候选、目标版本、业务原因 | 提交前明确“内容将固定” | PASS |
| UX04 | 提交后继续编辑 | 会发生什么 | 明确旧候选不会跟着草稿变化 | PASS |
| UX05 | 审核列表 | 我为什么能审核这条 | 只显示本人有资格且非本人提交的变更 | PASS |
| UX06 | 查看 Diff | 原来是什么、现在是什么 | 左右对比 + 业务名称优先 | PASS |
| UX07 | 判断风险 | 是否存在破坏性变化 | 风险和“消费者未知”分开表达 | PASS |
| UX08 | 审核决定 | 如何批准/退回/拒绝 | 决策按钮最后出现 | PASS |
| UX09 | 创建正式版本 | 批准的是哪份内容 | 发行前再次核对固定内容 | PASS |
| UX10 | 区分发行/生效 | 是否已经被业务范围使用 | 页面持续显示两种不同状态 | PASS |
| UX11 | 激活 | 会影响哪里 | 明确 Scope、旧版→新版和竞态保护 | PASS |
| UX12 | 激活超时 | 下一步做什么 | 原请求查询，不重复创建 | PASS |
| UX13 | 回退 | 回到哪个正式版本 | 只能从可信历史版本选择 | PASS |
| UX14 | 治理追溯 | 谁在什么时候做了什么 | 时间线展示完整链路 | PASS |
| UX15 | 无消费者登记 | 是否兼容 | 显示“未知”，不显示“全部兼容” | PASS |
| UX16 | 无权限 | 为什么不能操作 | 禁用/隐藏和服务端拒绝语义一致 | PASS |

## 五、必须修正的产品语言

| 技术词 | 用户界面推荐 | 何时出现 |
|---|---|---|
| Draft | 模型草稿 | 模型编辑 |
| SchemaSnapshot | 模型快照 | 历史/提交变更时 |
| ChangeSet | 模型变更 | 一级产品语言 |
| ReviewDecision | 审核结论 | 审核详情/记录 |
| SchemaRelease | 正式版本 | 版本管理 |
| Activation | 生效 | 生效范围 |
| Scope | 生效范围 | 用户选择影响范围 |
| candidateDigest | 内容摘要 | 高级详情 |
| approvalDigest | 审批依据摘要 | 审计详情 |
| idempotencyKey | 原请求 | 用户恢复操作时不必展示内部字段 |
| CAS / revision | 当前版本已变化 | 冲突提示 |
| UNKNOWN | 结果待核对 / 影响未知 | 用户可行动的状态 |

## 六、三个高风险交互

### 1. “批准”不能看起来像普通按钮

审核人必须先看到：

- 变更对象；
- 原版本与候选版本；
- 风险；
- 质量检查；
- 变更原因；
- 候选内容摘要。

然后才能作决定。

### 2. “正式发布”不能直接叫“发布并生效”

采用两个明确动作：

**创建正式版本** → **让指定范围生效**

这样用户不会误以为创建版本就会影响生产业务。

### 3. “回退”不能叫“撤销发布”

采用：

> **切回历史版本**

并在确认页说明：

> 这只改变模型当前生效版本，不会撤销已经发生的业务操作。

## 七、低保真原型边界

原型包含：

- 模型包概览；
- 我的变更；
- 待我审核；
- 变更详情；
- 创建正式版本；
- 生效范围；
- 生效确认；
- 治理记录；
- 超时恢复；
- 角色上下文；
- 正常与异常文案。

原型不包含：

- 真实 OIDC；
- 真实 RBAC；
- 真实 PostgreSQL；
- 真实 ChangeSet；
- 真实 ReviewDecision；
- 真实 SchemaRelease；
- 真实 Activation；
- 真实 SHA/JCS；
- 真实生产消费者。

## 八、UX-Low 通过门槛

进入 UX-High 前必须满足：

- [ ] UX01–UX16 无产品语义阻断；
- [ ] “模型草稿 / 模型快照 / 模型变更 / 正式版本 / 生效版本”新人可区分；
- [ ] 发行和生效不再混淆；
- [ ] 回退不被理解成撤销外部业务；
- [ ] 失败/超时路径能指导用户下一步；
- [ ] 权限不足和系统故障有不同处理；
- [ ] 所有技术术语只在高级详情出现；
- [ ] B0/B1/B2 每个未来实现 PR 都能对应一个完整用户故事；
- [ ] 低保真确认后再做视觉高保真，不提前开发 React。

**结论：推荐 UX-Low PASS（设计候选），但正式签收仍 Pending。**
