# OntoForge · 每轮功能交付说明模板（产品视角优先）

> **适用范围**：每次功能任务、修复任务与 PR 阶段收尾，在 `doc/implementation/` 生成一份交付说明，链接到 PR。
>
> **写作顺序**：先说**用户能做什么、解决什么问题、在哪操作、能看到什么**，再说质量、进度，技术细节放附录。面向产品负责人时，不以 Java 类、SQL、API、算法、测试脚本名作为功能名称。
>
> **真实性原则**：区分「新功能」「既有功能修复」「只增加测试保障」「文档改进」；区分「代码已实现」「自动化已通过」「用户实际环境已验收」「PR 已合并」「产品已发布」。这些状态不能互相替代。

## 全局定位与功能映射（每次必填）

先打开 [《MVP 功能全景与成熟度矩阵》](./OntoForge-MVP-产品功能全景与成熟度矩阵.md)，标明本 PR 是产品全景中的哪一小步：

| V1.3 功能编号及子功能 | 用户体验：预计实现 → 本轮实际实现 | 上轮成熟度 → 本轮成熟度 | 性质（新功能 / 修复 / 测试加固） | 尚未覆盖的同域功能 |
| --- | --- | --- | --- | --- |
| 示例：F04 历史版本留存（不是整个 F04） | 能冻结并打开旧版 → 已完成 | 未实现 → 基础可用·加固 | 新功能 + 可靠性加固 | 审批、正式发布、激活、回退 |

- 必须明确属于 **S0 工程型 / P0 建模产品型 / P1 工业业务价值型 / P2 Agent 增强 / P3 受控行动** 的哪个层次。
- **不准因某个子功能自动化完善，就把整个 F 编号标为“已完成”。**
- 记录实际用户入口、已见结果、原范围、剩余差距，便于从局部交付回到全局进度。

## 一、30 秒看懂本轮交付（必填）

| 产品负责人最关心的问题 | 用通俗语言回答 |
| --- | --- |
| **本轮目标** | 用一句用户故事说明要解决的业务问题 |
| **本轮真正交付了什么** | 1～3 个产品能力或修复点；如果只增强测试，明确说明**没有新增操作功能** |
| **用户现在能做什么** | 使用「打开/创建/保存/检查/查看/比较/恢复」等操作动词 |
| **当前产品状态** | 例如：已开发且自动测试通过；PR 待合并；Windows 实机尚未验收；未发布 |
| **下一步最重要的事** | 一句话说明下一件影响交付的事，以及为什么 |

> 禁止把「通过 17 项 Java 测试」「新增数据库字段」「实现 SHA-256」直接写成产品功能摘要；这些是技术证据，不是用户价值。

## 二、用户可直接感知的功能（必填）

| 功能名称（产品语言） | 解决的问题 | 使用入口 / 用户操作 | 用户能看到的结果 | 交付性质与状态 |
| --- | --- | --- | --- | --- |
| 示例：模型版本留存 | 模型修改后找不到旧版 | 建模工作台 → 完整性检查 → 保存历史版本 | 看到一条不可编辑的历史记录，可重新打开 | 新功能；已通过自动化；实机待验收 |

- **已有功能**与**本轮新增/修复**分开写，避免把历史功能重新算成本轮成果。
- 每个功能至少写出一个可感知的最终结果；如果是后台可靠性增强，写清失败时用户看到的效果，不要假装新增了按钮。
- 功能名称使用与页面一致的产品词汇；必要的技术词汇在附录给出一次解释。
- 状态优先写中文：**已实现／自动化通过／实机未验收／未实现／已发布**，不要只写 CODED、Gate、Head、CAS。

## 三、一个完整的用户故事（必填）

按用户真实操作先后，写 3～7 步：
1. **从哪里开始**：页面/菜单和示例业务对象。
2. **做什么**：点什么、填什么，先后依赖是什么。
3. **看到什么**：成功后的数据、页面、提示及历史记录。
4. **如果失败**：发生冲突、网络异常、非法内容时，用户下一步怎样安全恢复。
5. **什么不等于成功**：例如「保存历史版本」不等于「模型正式发布」。

> 建议同时描述一个正向故事、一个关键异常故事。复杂技术术语不放在正文流程中。

## 四、本轮实际改动 vs. 技术保障（必填）

| 类型 | 本轮改了什么（产品语言） | 对用户的价值 | 是否新增操作能力 |
| --- | --- | --- | --- |
| 新功能 / 修复 / 稳定性测试 / 文档 | | | 是 / 否 |

> 尤其是「新增测试」：描述为**提升已有功能的可靠性和错误保护**，而不是凭空增加一项产品能力。

## 五、验收结果：哪些可信，哪些还不能签收（必填）

| 产品层面需要确认什么 | 证据或可复现方法 | 当前状态 | 是否需要用户参与 |
| --- | --- | --- | --- |
| 示例：历史版本创建与比较确实可用 | 真实后端 + 数据库 + 浏览器端到端用例 | 自动化已通过 | 可抽检 |
| 示例：Windows 本机重启后版本仍存在 | 本机独立测试库，停/启服务后打开旧版本 | 未验收 | 是 |

- 若展示技术报告，在表后补**简要证据**：PR、最新被验证 SHA、CI 链接、通过/失败数量。
- 不在 Linux 的模拟重启测试后写「Windows 11 本机已验收」。
- 若最新 Head 还有 CI 在运行，写 **待最终确认**，不要引用旧 SHA 冒充最新结果。
- 不把 Mock 原型当成真实功能。

## 附录：技术证据与术语（只给需要深入追踪的人）

- 核心实现文件、接口、数据库迁移、兼容性合同、具体测试项、错误码、代码 SHA。
- 「模型历史版本」可在技术层称 **SchemaSnapshot（模型快照）**。
- 「版本内容校验」对应 **JCS/SHA-256（规范化与摘要）**。
- 「保存冲突保护」对应 **revision / CAS（修订冲突检查）**。
- 「历史版本对比」对应 **Diff（结构差异）**。
- 「自动测试通过」不等于「用户实机通过」；「合并代码」不等于「产品发布」。

**交付质量要求**：产品负责人读完前六节，应无需阅读 Java/SQL/测试日志，就能准确回答「做了什么、能怎么用、还有哪些不能用、下一步做什么」；技术人员仍可从附录追溯到真实证据。
