## Standards（协议约束与实现）

仓库未发现独立编码规范，以下依据 V1.2 §9 的“事务边界、幂等、超时恢复”和实验 README 的“Claim Token 区分过期占用”，不提出风格性阻断。

1. **[P1] 旧 Worker 可以覆写新 Worker 已确认的终态。** [run_pg_poc.py L231–236](https://github.com/gitfortian/ontology-system/blob/d32ab44ce85a8003c56b5529c586c14d24dc9ce8/experiments/pg-runtime/run_pg_poc.py#L231-L236)：`mark_state` 仅按 ID 更新 Attempt/Outbox，无 token 或前置状态条件。可发生：W1 通过入口检查后暂停 → 租约过期 → W2 接管并置为 `VERIFIED/DONE` → W1 的迟到网络错误执行 `mark_state(UNKNOWN)` → 变成 `UNKNOWN/UNKNOWN`，但成功 Overlay 已存在。入口一次 token 检查无法约束后续写入。建议用当前 claim token 和允许的前置状态做条件更新，保护终态单向性；增加“接管成功后旧 Worker 才超时”的确定性负例。这是报告 G3 所述剩余竞态门禁的一个具体失败反例。

2. **[P2] 同 Key 的首次并发创建不满足幂等返回合同。** [run_pg_poc.py L137–158](https://github.com/gitfortian/ontology-system/blob/d32ab44ce85a8003c56b5529c586c14d24dc9ce8/experiments/pg-runtime/run_pg_poc.py#L137-L158)：两个调用都可能先查到幂等记录不存在；不存在的行无法由 `FOR UPDATE` 锁住。即便后续 SourceFact 行锁串行化了两者，后来的事务也不会重查幂等记录，最终普通 INSERT 抛 `UniqueViolation`。唯一约束防止了重复记录，却没有保证两个相同请求返回同一个 Attempt。建议使用冲突安全插入后读取胜者，并核对 payload/requester；补同 Key 并发首次创建及不同身份冲突测试。[PostgreSQL 的隔离与冲突语义](https://www.postgresql.org/docs/17/transaction-iso.html)支持该交错分析。

## Spec（实测承诺与故障闭环）

1. **[P1] 先做漂移阻断，会让已发生的远端效果无法完成对账。** 报告 §2.1 承诺“新 Worker 先查远端回执”，但 [dispatch L277–282](https://github.com/gitfortian/ontology-system/blob/d32ab44ce85a8003c56b5529c586c14d24dc9ce8/experiments/pg-runtime/run_pg_poc.py#L277-L282) 在查回执前执行 `check_contract`。顺序：远端 HOLD 已提交 → 本地确认前崩溃 → 来源追平并增加 revision，或 Policy 更新 → 回收租约 → dispatch 直接标为 `BLOCKED_NEEDS_REVIEW`，没有查询回执。此后即使人工 reconcile 取得合法回执，[L246–247](https://github.com/gitfortian/ontology-system/blob/d32ab44ce85a8003c56b5529c586c14d24dc9ce8/experiments/pg-runtime/run_pg_poc.py#L246-L247) 仍拒绝为 `LATE_INVALID_RECEIPT`。建议将“记录已经发生的外部事实”与“授权发起新副作用”分开：先只读对账；如仍需发送，再检查最新合同。补远端提交后崩溃与来源/策略漂移的组合测试。
