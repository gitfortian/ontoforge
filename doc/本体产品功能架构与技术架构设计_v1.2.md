## 0. 修订决策：从 OWL-first 倾向转为企业运营本体

**路线决定（提请评审）**：以自主定义、强类型且可审计的 **Native Ontology Schema / AST** 作为模型定义和版本权威，原生支持 ObjectType、Property、LinkType、DataBinding、ObjectSet/Query、Function、Action、Policy。OWL/RDF/SHACL/SPARQL 是按需启用的标准语义交换和推理适配器，不是所有模型发布、对象查询或 Action 执行的必经路径。

**不变的产品目标**：为制造企业把 ERP、MES、QMS、PLM、WMS、EAM 等碎片化系统映射为稳定的业务对象和关系，支持可信查询、业务计算、人工/Agent 协作以及安全可审计的业务操作；不替代企业原业务系统。

**V1.1 保留**：F01–F29 原有编号、八大功能域、四层领域本体包、语义术语与共识、变更审查、质量门禁、来源证据、受控行动、三条黄金故事、模块化单体起步与先验证再扩展的开发原则。

**V1.2 真正改变**：Schema 不再必须编译为 RDF/OWL 才能发布；Native Object Runtime 和 ObjectSet/Query 提升为核心系统；Connection/Binding/Identity 是一等工程契约；Function 和 Action 是产品原生定义，且与执行运行时分离；Jena/TDB2 成为可选专业适配器；OWL 复杂公理不再是 P0 交付的前提。

## 1. 为什么不把 OWL 作为全平台核心？

### 1.1 定义问题：不是 OWL 能否用于商业，而是什么应该成为产品权威

OWL 是 W3C 标准描述逻辑本体语言，适于表达类、属性、继承、等价、限制、公理和特定推理。RDF/OWL 可以服务企业知识图谱、数据互联和专业语义校验，并非只属于学术界。Stardog、GraphDB 等商业产品也建立在标准语义栈上。

但 OWL **不是对象服务、分布式存储、任务引擎、业务事务或授权执行框架**。制造业运营本体要同时定义数据接口、身份、对象集合、过滤聚合、来源绑定、动态状态、函数版本、外部写回、审批、审计、错误补偿。即使全部先映射到 OWL，也仍要建设这些工程层；反之要让 OWL 的开放世界语义成为唯一运行真相，还需要额外处理企业封闭世界校验与业务流程之间的边界。

因此本产品不以“能表达多少 OWL 2 DL 公理”为核心竞争指标，而以“能连接多少可靠的企业对象、可执行多少可审计的业务能力、能帮助 Agent 做多少可信决策”为核心。

### 1.2 方案 A / B / C 对照

| 维度 | A：全平台 OWL 为权威 | B：Native 为权威 + 标准适配（采用） | C：纯无类型 JSON + 图展示（拒绝） |
|---|---|---|---|
| 对象/关系定义 | OWL Class/Property + 自定义扩展 | 原生强类型 ObjectType/Property/LinkType | 临时 JSON |
| ObjectSet、过滤、聚合 | 需要独立工程层和语义映射 | 原生查询 AST、权限与计划器 | 接口各自处理 |
| 海量对象与时序 | 需独立存储/索引与同步方案 | 按需物化、联邦查询和时间索引 | 缺统一合同 |
| Function/Action | 自定义注解与另建执行体系 | 一等契约与独立受控运行时 | 业务硬编码 |
| 强类型/兼容性 | 借助语义工具，仍需业务门禁 | 原生类型检查、Schema Diff、发布 Gate | 高风险 |
| 与 OWL 生态交换 | 原生优势 | 可声明子集的有损/无损转换 | 能力弱 |
| 核心复杂度 | 双重语义/运营建模成本 | 将运营需求放在模型中心 | 初期易做、长期不可控 |
| 本产品适配性 | 不是最佳起点 | **首选** | 不满足可治理本体要求 |

### 1.3 实际运行语义不一致之处

- **开放世界与业务验收**：OWL 不因事实缺失就推断其为假；生产操作却必须能拒绝“必填证据不完整”“质量状态未知”“审批人无权”等情形。
- **实例关系不由类型自行产生**：存在 ProductLot→CustomerOrder 的 LinkType，并不能推出 LOT-001 确实影响 ORD-0088；影响关系要由有证据且被授权的源映射或实例事实确认。
- **业务行动不是逻辑蕴含**：即使知识推理认为某批次可能存在风险，也不能直接触发 MES/QMS 冻结。必须经独立 ActionPolicy、授权、幂等和核验。
- **计算和时间语义**：动态库存、可交付量、实时设备告警、复杂优化以及 Function 资源限制不是靠标准 OWL 语法就能替代的。
- **不等于抛弃严谨性**：原生 Schema 仍要保证稳定标识、类型兼容、约束、引用完整、来源证据、版本治理和权限一致。

### 1.4 为什么不能把 OWL 全面删除？

行业和客户可能提供 RDF/OWL、要求标准本体交换、使用 SHACL 检查或需要特定逻辑推理。完全放弃标准接口会损失互操作与专业知识资产。因此我们建设明确的 Semantic Adapter：按被支持的子集导入/导出，形成 conversion report；不支持的公理要保留诊断、要求确认或拒绝，不能静默丢失。适配器不能回写 Native 权威发布制品。

### 1.5 决策风险与可反驳条件

原生模型的代价是我们自己负责强类型语言、约束和版本语义；不能将本体降级为自由 JSON。若试点证明高度复杂的 OWL 规则是主要用户刚需、标准交换必须无损且比 ObjectSet/Action 更优先，应重新评估专业 OWL Workspace 或扩展更深的标准表达能力，而非硬改现有运营元模型。

**结论**：OWL 商业有效；但对于“工业企业对象—分析—行动—Agent”产品，它是有边界的标准语义能力，不应成为所有业务能力的权威执行语言。

### 3.1 五条必须连续的用户旅程

1. 业务专家以领域包或从空白定义 ObjectType、Property、LinkType，能够验证和保存，不需要懂 OWL。
2. 数据工程师选择 ERP/MES/QMS 源、创建 Binding、定义 IdentityRule，校验样本和来源变化，明确更新/撤回。
3. 业务分析师用 ObjectSet 筛选批次，沿 Link 查询订单，聚合风险，保留来源/时态/准确性声明。
4. 计算开发者发布 Function，允许明确的只读计算、输入输出签名、成本/超时上限和结果溯源。
5. 被授权用户或 Agent 通过 Action 申请业务写回，完成审批、执行、核验与审计；不得从 Function 的语义可调用性自动推断行动权限。

## 4. 分层技术架构与真相源

~~~mermaid
flowchart TB
  USER["Studio / SDK / App / Agent"]
  SCHEMA["Definition：Native Registry / Schema AST / Review / Release"]
  BIND["Binding：Connection / Mapping / Identity / Evidence"]
  OBJ["Object Runtime：Object / Link / ObjectSet / Query"]
  FUNC["Function & Analytics：Signature / Metric / Safe Runtime"]
  ACTION["Action & Capability：Policy / Approval / Execution / Receipt"]
  STORAGE["Adapters：SQL / Search / Graph / Timeseries / Object Store / Federation"]
  OWL["Optional RDF / OWL / SHACL / SPARQL Adapter"]
  GOV["Cross-cutting：Auth / Quality / Audit / Observability"]
  USER --> SCHEMA
  SCHEMA --> BIND
  BIND --> OBJ
  OBJ --> FUNC
  FUNC --> ACTION
  OBJ --> ACTION
  OBJ --> STORAGE
  BIND --> STORAGE
  SCHEMA -.明确转换子集.-> OWL
  OBJ -.可选择对象子集.-> OWL
  GOV -.策略.-> SCHEMA
  GOV -.策略.-> BIND
  GOV -.策略.-> OBJ
  GOV -.策略.-> ACTION
~~~

| 平面 | 唯一权威与数据边界 | 首期行为 |
|---|---|---|
| Definition | Native Schema AST、Package、Release、Policy/审查元数据为权威 | 创建、类型检查、版本化、审查、发布 |
| Binding | 连接器、来源字段、映射/身份规则和来源证据为权威 | 契约/部分实现；不自动把所有数据搬迁 |
| Object Runtime | 对已授权源数据的可查询对象快照/引用/索引及关系事实负责 | P0 内核接口、P1 查询实体 |
| Function Runtime | FunctionDefinition、版本、执行输入、调用者和结果归属 | P0/P1 契约，P2 执行 |
| Action Runtime | ActionDefinition、风险/审批、外部副作用与执行核验 | P0 契约预留，P2/P3 实施 |
| Semantic Adapter | 明确映射后的 OWL/RDF/SHACL 派生图或导入候选 | **按需加载，不成为 P0 必装组件** |

业务源系统仍是其主营数据的权威。Object Index 是**带版本、时态、来源及授权的可重建投影**，不是第二套不受控的主数据。对于平台内部产生的审核记录、操作决策/回执和经批准的对象编辑，应明确平台自身事实的权威域及同步/回写协议。

**存储取舍**：PostgreSQL 管理元数据/Registry/事务审计是候选默认；索引搜索引擎、关系图引擎、时序库、缓存和对象存储待试点数据规模再选型。Jena/TDB2 可由专业语义适配器单独启用，不是 Object Runtime 的强制底层。




## 5. 原生元模型：从 Schema 到运营能力

V1.1 的 EntityType/DataProperty/ObjectProperty/DisjointClasses 是历史 DSL V0.1 最小子集，其机器 Schema 尚未正式实施。**V1.2 不删除旧文件，而是要求下一步提出 Native DSL/AST V0.2，不能直接把旧 Schema 编码成不可变的 OWL-first 后端接口。**

| 原生定义 | 关键字段与责任 | 与 OWL 的关系 | 阶段 |
|---|---|---|---|
| OntologyPackage | 包、版本、依赖锁、Release、发布摘要 | 可交换部分模型 | P0 |
| ObjectType | typeId、apiName、label、primaryKey、propertyRefs、linkRefs | 部分可映射 owl:Class | P0 |
| Property | propertyId、ownerType、valueType、required、constraint、security | 简单属性可映射 RDF 值类型 | P0 |
| LinkType | linkTypeId、sourceType、targetType、roles、cardinality、linkSource、evidence | 简单二元关系可映射 ObjectProperty | P0 |
| InterfaceType | 接口定义、共有形状、实现对象与能力契约 | 不必等同 owl:Class | P1 |
| Constraint | 静态类型、值域、范围、基数、兼容规则 | 部分可映射 SHACL，非强制 | P0 |
| SourceConnection | sourceId、type、capabilities、authRef、scope、health | OWL 不表达连接运行 | P1 |
| BindingDefinition | 源字段/事件/关系映射、版本、刷新/失效策略 | 可选择做语义映射投影 | P1 |
| IdentityRule | 主键、跨源身份策略、置信证据、冲突裁决 | 不自动产生 owl:sameAs | P1 |
| ObjectSetDefinition | rootType、typedFilter、traversal、projection、timeScope、policy | Native Query AST 优先 | P1 |
| FunctionDefinition | 函数签名、版本、执行源、依赖、效果和预算 | 不能只靠 OWL 公理执行 | P2 |
| ActionDefinition | 操作签名、目标类型、前置、风险、审批、执行/核验 | 独立的受控副作用机制 | P2/P3 |
| Policy/Evidence | 来源、主体、操作范围、审核与溯源要求 | 安全与证据不由推理代替 | P0 起 |
| Term/Concept/Alignment | 术语/概念/映射/审核候选 | 可选 RDF/SKOS 互操作 | F24/F26 |

**元模型不变量**：ObjectType ≠ ObjectInstance；LinkType ≠ LinkFact；PropertyDefinition ≠ Observation；FunctionDefinition ≠ ActionExecution；未经审核的 AlignmentCandidate ≠ 真实同一性。类型和关系有稳定 ID 和 API 名称，后者更改必须兼容性评审。原生对象不要求全部使用 HTTP IRI；公开 IRI/URI 可作为受治理的映射字段，支持标准生态。

**P0 边界**：先建 Package、ObjectType、Property、LinkType、Constraint、Registry、Draft/Review/Release；为 Binding/ObjectSet/Function/Action 明确引用与版本协议，不等于本轮把所有执行器和存储都实现出来。

### 5.1 原生 DSL 设计示意

~~~yaml
package: manufacturing.quality
version: 0.2.0
objectTypes:
  - id: product-lot
    apiName: ProductLot
    primaryKey: lotId
    properties:
      - {id: lot-id, name: lotId, type: string, required: true}
      - {id: quality-status, name: qualityStatus, type: enum, options: [PENDING, HELD, RELEASED]}
  - id: customer-order
    apiName: CustomerOrder
    primaryKey: orderId
linkTypes:
  - id: lot-affects-order
    from: product-lot
    to: customer-order
    cardinality: MANY_TO_MANY
functions:
  - id: count-affected-orders
    effect: READ_ONLY
    input: ProductLot
    output: integer
actions:
  - id: hold-product-lot
    target: product-lot
    riskPolicy: quality-review
~~~

此 YAML 仅用于产品/架构讨论，**不是可直接运行的正式 V0.2 Schema**。Function/Action 仅声明签名和政策引用，不能因此获得执行权限。下一步应为 Native DSL/AST V0.2 生成 JSON Schema、规范化 AST、迁移映射与正反例。

## 6. 数据连接、绑定、身份与来源证据

**Connection** 描述 ERP/MES/QMS/时序/消息/API/文件等连接的能力、凭证引用、健康与权限；**Binding** 将物理源字段、记录主键、事件或链接映射为 ObjectType/Property/LinkType 的事实；**IdentityRule** 处理多源同一实体，不能因为两个表都包含 customer_id 就认定同一客户。

Binding 的 sourceSchemaVersion、mappingVersion、refreshMode、sourceKey、fieldMapping、linkMapping、dataQualityPolicy、securityScope 必须可追溯。来源漂移触发影响分析和重审；撤权后已索引数据必须按策略重新授权/失效。跨源低置信匹配只进入候选，不参与生产 Agent 默认上下文。

| 读取/索引模式 | 适用场景 | 工程纪律 |
|---|---|---|
| 直接联邦 | 来源查询快、实时性重要 | 推送过滤、授权、超时/成本预算 |
| 物化对象索引 | 高频搜索、跨源筛选/聚合 | 增量刷新、watermark、可重建/撤权 |
| Link Index | 批次→订单→供应商等追溯路径 | 来源、有效时间、关系撤销、路径成本 |
| 外部引用 | 时序大明细、视频、文件 | 稳定对象引用和授权，不强制 RDF 化 |
| 混合 | 真实企业大多数应用 | 查询执行计划可解释、标记数据新鲜度 |

既有源系统仍是自身业务数据的权威。对象索引是经管理的查询投影，不是另一套无同步纪律的主数据。平台写入的审批、评论、操作决策、回执等由平台明确拥有独立事实权威。

## 7. ObjectSet / Query Runtime 是核心，不是 SPARQL 的薄封装

ObjectType 定义对象类别；Object 是某个真实实例；ObjectSet 是按类型、过滤和授权计算出来的一组实例；QueryResult 是某个模型/映射/时间/权限上下文下的结果。这四者不能互相替代。

| 原生查询操作 | 输入/输出 | 必备 Gate |
|---|---|---|
| Filter/Search | ObjectType、Typed Predicate → ObjectSet | 字段类型与读取授权 |
| Traverse/Join | ObjectSet、LinkType、方向、深度 → ObjectSet/LinkPath | 来源与边权限、路径预算 |
| Project/Enrich | 选定字段与外部来源 → ObjectView | 属性级脱敏和撤权 |
| Aggregate | 计数/分组/求和等 → MetricResult | 小样本泄漏、结果精度与来源 |
| Sort/Paginate | 排序键/稳定游标 → Page | 权限、快照版本、成本 |
| Explain/Evidence | QueryPlan → 路径、来源、准确性、时间 | 调试信息授权 |

**查询必须区分精确、近似、部分结果和过期结果**，不能把聚合估值当成确定事实。Palantir 的 Object Set Service 公开文档也明确存在高基数聚合近似与返回准确性描述的情况，我们应以 Accuracy/Completeness/Freshness 明示结果质量。

**性能不是无限制图遍历**：最大关系深度、对象集上限、执行计划成本、超时、取消、缓存生命周期和审计均为 Query API 契约。权限必须在索引、遍历、聚合中间结果及缓存生效，而不只是最终表格页面隐藏字段。

首个业务目标：将 QMS 中冻结批次组成 ObjectSet → 跨 MES 追溯相关产品 → 通过 ERP 订单映射获得受影响待发货订单 → 查询订单数/金额/优先级并显示来源与时间。当任一源不可达时显式报告部分结果，不能编造订单。

## 8. Function 和 Action 是原生一等能力

**FunctionDefinition**：functionId、version、input/outputSchema、objectTypeRefs、dependencyVersions、implementationRef、effectClass、timeLimit、resourceBudget、requiredPermissions。可以读取 ObjectSet、遍历 Link、计算风险或模拟结果。我们默认 Function 是 READ_ONLY；如果需要修改对象或者外部系统，必须由具备风险策略的 Action 明确包装、授权并审计，不能通过查询函数隐式越权。

**ActionDefinition**：actionId、targetTypes、parameters、preconditions、requiredEvidence、riskClass、approvalPolicy、executorRef、idempotencyPolicy、verificationPolicy。它定义可用的业务动词，但不等于可执行权限。典型行为 HoldBatch、CreateInspectionTask、NotifySupplier、ReleaseShipment 必须重新评估调用主体、目标对象、当前状态及授权范围。

~~~mermaid
stateDiagram-v2
  [*] --> Proposed
  Proposed --> Validating
  Validating --> Rejected: policyOrEvidenceFailed
  Validating --> PendingApproval: approvalRequired
  Validating --> Ready: policyApproved
  PendingApproval --> Rejected: deniedOrExpired
  PendingApproval --> Ready: humanApproved
  Ready --> Running: executeWithIdempotency
  Running --> Succeeded: verified
  Running --> Failed: confirmedFailure
  Running --> Unknown: timeoutOrUncertain
  Unknown --> Succeeded: reconciledSuccess
  Unknown --> Failed: reconciledFailure
~~~

**Unknown 不是 Success**；先对账外部执行回执再考虑重试。Schema Release 回滚不能自动撤销 ERP/QMS 已经发生的真实副作用。首期不直接支持物理设备闭环控制。

Palantir 官方 Function-backed Actions 可用函数支撑复杂的多对象更改，说明“计算能力”和“行动入口”可以联动；我们的产品安全设计仍必须把函数版本、动作授权和执行回执拆开。

Agent 通过 Capability Registry 获取按用户/服务主体授权的可查询 ObjectSet、可调用 Function 和具风险等级的 Action。**能看见批次 ≠ 能修改批次 ≠ 能让设备执行动作**。

## 9. 模型、数据与行动一致性及安全

- Native Schema Release：Draft→Validate→Review→Approved→Published/Active→Deprecated；审批绑定规范化 AST、依赖锁、质量门禁与签名摘要。
- Binding Version、ObjectIndex Snapshot、FunctionVersion、ActionVersion 与 SchemaRelease **分别版本化**；关键查询/行动记录应携带联合版本上下文。
- Source、Object、Property、Link、Filter/Traverse 中间结果、Function、Action、SDK/MCP、Agent 全部实施服务端授权。来源撤权和模型撤销需要穿透索引、缓存、图投影及长任务。
- 本体编译、索引激活、外部操作均需事务边界、幂等、超时恢复；不可假定 PostgreSQL 和外部图/索引引擎天然共享 ACID。
- 不因为不采用 OWL 就取消强类型、关系基数、取值枚举、模型比较和领域约束；原生约束需要自己的规则语义、解释及回归测试。



## 10. OWL/RDF/SHACL 适配层：保留标准互操作而不让其支配内核

### 10.1 能力范围表

| Native 能力 | 标准语义投影 | 导出策略 | 导入策略 |
|---|---|---|---|
| ObjectType | 简单类型可转 owl:Class | 可无损表达基本类身份和层级的子集 | 识别合法已支持的类；不可直接执行复杂公理 |
| Property（简单值） | 可映射 datatype property/XSD | 基本类型可对应，平台特有数据约束可能有差异 | 显示 datatype/形状约束转换报告 |
| LinkType（简单二元） | 可映射 object property | 无额外时态/来源/审批的基本关系可投影 | 带复杂边属性的场景不能悄悄丢失 |
| InterfaceType / Contract | 未必有直接对等 OWL 语义 | 必须说明丢失的多态/能力含义 | 不以 OWL 等价类伪造产品接口 |
| SourceConnection / Binding | RDF 映射技术可选；不属于基本 OWL Schema | Native 配置不随便序列化为公理 | 导入后仍需新建受授权来源绑定 |
| Identity / Temporal / Evidence | 可借 RDF/PROV 等特定词表表示部分信息 | 必须标注事实粒度、时态与版本 | owl:sameAs 需要身份风险审查 |
| ObjectSet / QueryPlan | 不直接等同 OWL Class 或 SPARQL 文本 | 不将动态集合硬写成“永真类公理” | 转换为查询需要独立执行计划 |
| FunctionDefinition | 无通用同等 OWL 执行语义 | 只可导出描述性元数据和扩展 | 无法导入可执行代码时显式 UNSUPPORTED |
| ActionDefinition / Policy | OWL 不实现授权和外部写回 | 可导出描述但不授予可执行权 | **任何导入的动作都不可自动执行** |
| SHACL | 专业 RDF/实体质量检查 | 按适配 Profile 校验 | 不取代 Native Quality Gate |

### 10.2 适配质量等级

- **LOSSLESS_SUPPORTED**：指定版本 Profile 范围内的模型信息与语义等价可完整表示，且双向往返测试通过。
- **PARTIAL_SUPPORTED**：可以表示子集，明确列出未转换实体/属性/约束、查询语义差异；默认需要用户确认。
- **UNSUPPORTED**：涉及无法表达或不可安全转换的内容，阻断生产导入/导出；不得静默丢弃。
- **ERROR**：IRI 冲突、无效本体语法、未授权来源、无效类型、验证失败，返回结构化诊断。

所有 Adapter Artifact 必须标记 nativeReleaseId、adapterVersion、profile、artifactDigest、sourceEvidence 和 lossReport。**投影不是发布真相源**：用户修改专业 RDF 后也只能作为导入候选，通过 Native ChangeSet、质量门禁和审批进入权威模型。

SHACL/RDF 可作为特定领域/Profile 的检查机制，不能代替原生平台的必填、类型、权限、真实业务 Action 状态机。GB/T 48000.3—2026 是标准数字化本体的专业要求：建议未来通过 Standard Document Ontology Profile 落实其规范性附录 A，不强行把章、条、信息单元注入所有制造 ObjectType。

## 11. 三条黄金故事的 V1.2 验收方法

### 11.1 黄金故事 A：制造质量异常→订单影响→受控处置（主线）

1. 在 Studio 中以领域包创建 ProductLot、MaterialLot、Supplier、WorkOrder、CustomerOrder、QualityEvent 的原生类型/属性/LinkType。
2. 连接 QMS/MES/ERP 样例来源，审查主键/跨源身份及 DataBinding，显示来源时间和不确定性。
3. 查询不合格批次 ObjectSet，逐层遍历受影响物料、产品批次、工单和订单；不预先要求全量 RDF 化。
4. 通过 Function 计算订单数量、金额和处置优先级；若数据源缺失或聚合近似，返回准确性/完整度标签。
5. 人员/Agent 提议 HoldBatch / CreateInspectionTask；按风险政策与权限审批，执行 QMS/ERP 沙箱操作，产生可验证回执与对账记录。
6. 处理变更、重跑、失败恢复、源撤权与审计回放，签收整个闭环。

**硬性反例**：无法仅凭同名合并批次；无来源 LinkFact 不进入影响链；字段撤权后不得通过对象聚合泄露；Action 超时不能直接标成功；通过 Function 不得绕过 Action 权限。

### 11.2 黄金故事 B：设备异常→维护排程

Equipment、SensorRef、Observation、Alarm、WorkOrder、MaintenancePlan 组成的业务模型，不能要求设备高频历史数据全部进入图存储。对象索引保留设备身份与关联、时序引用按需访问，Function 计算异常窗口和风险，Action 只能按权限创建维护工单（MVP 不直接控制 PLC）。

### 11.3 黄金故事 C：同名异义→语义对齐→权限撤回

CRM 的签约客户、ERP 的结算客户、售后的服务受益人分别有业务定义。Term/Concept/IdentityRule 发现冲突，低置信对齐只能进入候选；审查批准映射后才能作为 Query/Context 来源。撤回某系统权限后，查询、聚合、缓存、图投影、MCP 都必须立即在规定一致性界限内禁用其数据。

## 12. P0–P4 路线与技术验收 Gate

| 阶段 | 交付闭环 | 必验指标与负例 | 明确不做 |
|---|---|---|---|
| **S0 工程底座** | 选择 Yak Ops 工程组织/前端壳/用户 Workspace 的安全裁剪，Java 服务启动、迁移、CI | 独立启动登录/Workspace；无同步引擎强制依赖；安全和许可证检查 | 直接完整 Fork 数据同步产品 |
| **P0-A Native Model** | ObjectType/Property/LinkType、Package/Registry、Native DSL/AST V0.2、保存验证 | 同名/重复 ID、类型/关系错误、跨空间写入、依赖锁冲突被拒绝 | 以 OWL 编译作为保存前提 |
| **P0-B Model Governance** | Schema Diff、Review/Approval、Quality、Release/Artifact、兼容校验 | 旧审批失效；变更摘要一致；发布失败不可激活 | 全功能 RDF 推理器 |
| **P1 Data Binding / Objects** | 首批 QMS/MES/ERP Connector、Object/Link Index、ObjectSet/Query | 真实来源身份、映射撤回、基本百万级负载 POC（阈值实测约定） | 先自研分布式数据库 |
| **P2 Function / Agent** | 版本化 Function、ObjectSet 计算、Agent Context/Capability | 查询/函数不可越权；资源/超时受限；结果溯源 | 任意 Agent 自主写业务系统 |
| **P3 Action Closed Loop** | 审批策略、Action 适配、幂等/补偿/核验、质量异常主线 | 拒绝、超时 UNKNOWN、重放、撤权及回执验证 | 高危 OT 自动闭环控制 |
| **P4 产品化** | 行业包市场、可扩展运行时、可选 RDF/OWL 专业适配、企业运营管理 | 复杂模型包升级、跨环境发布与高并发/容量实测 | 未有客户需求就做完整 Foundry 规模 |

阶段名称 S0、P0–P4 延续此前规划；“百万级”仅为候选性能测试规模，**不是当前性能承诺**。先以真实制造样本进行定量 POC，再冻结 SLA、引擎选型与集群部署策略。

**S0 与 P0-A 应分为独立可验证的 PR**：第一个交付可安装的工程底座，第二个交付可运行 Native Schema 创建→校验→保存→读取主线；不可只合入大量抽象类却看不到实际闭环。

| ADR | 决策建议 | 借鉴/取舍 | 验收方式 |

| **ADR-32 Semantic Security** | 元数据与实体事实权限分层；全链路同策略 | 权限进入中间结果与行动 | 横向越权、来源撤权、Function/SDK 旁路测试 |

**V0.1 合同地位**：保留历史评审成果供兼容与迁移参照；正式 P0-A 代码实现应等待 Native DSL/AST V0.2 签收，提供从 V0.1 中 EntityType→ObjectType、DataProperty→Property、ObjectProperty→LinkType 的已声明可转换子集。复杂 owl:equivalentClass/DisjointClasses 进入专业语义扩展，不静默丢失。
