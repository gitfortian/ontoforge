## Motivation

M14 #53 计划以质量/采购两个领域及第三种自定义对象证明通用能力，方向正确。但“Extended M12–M14”与“Core 签收依赖 M0–M11”容易让团队误以为 Core 不需要最终综合验收；第三类型通过也不能证明消除了所有领域硬编码。

用户需要一个可复验结果：从空的**独立测试模型包**开始，在同一构建下完成建模、快照、绑定、对象读取、集合过滤/分页、关系遍历和证据查看；再建立另一领域，不修改 Java/TS 业务代码。测试失败、来源漂移和未知状态也必须可见。M12 Action 与 M13 Agent 可独立验收，不能阻塞纯 Core 查询闭环。

当前 M2/M3 已合并真实质量场景代码和测试，作为回归基线；它们的固定角色/字段选择不能充当通用采购故事已经通过的证据。已有 Windows 隔离自动化也不能代替用户既有安装或人工 UAT。

非目标：本提案不新增服务/API/数据库表/CI 工作流、不修改历史测试断言、不把合成数据验收推广成生产连接器/工业现场安全证明。

## Public Interfaces

**运行时公共 API/Schema/数据库变更：None。** 本次只定义评审和验收证据的消费格式；后续依真实交付记录在既有总账和 PR，不提前造报告服务。

| 验收记录字段 | 要求 |
| --- | --- |
| 身份 | 功能 issue、OFIP 状态/明确决定链接、实现 PR、review base SHA、tested head SHA、构建产物身份 |
| 环境 | OS、Java/Node/PG/浏览器版本、隔离库标识、运行 profile、来源夹具版本；不含密码、token、连接秘密 |
| 场景 | 操作入口、输入模型/Binding、预期集合与来源证据、实际结果、错误恢复、回归范围 |
| 结果 | 每个范围分别 `PASS / FAIL / NOT SELECTED / NOT RUN`；外部阻断作为原因说明，不改成成功 |
| 签收 | 自动执行者/CI Run 与人工操作者/产品决议分开；人工签收必须有真实记录，不由 AI 代签 |
| 保留 | 报告/截图/日志的链接、摘要及保留位置；证据过期或缺失时标明缺口，不能仅留绿色徽章 |

“tested head”标识实际 checkout；CI 测试合并提交时同时保存 PR source head 和 merge SHA，不能把二者混为一个。后续改动涉及受测范围则重验对应场景，不复用旧绿灯证明新代码。

## Proposed Changes

### 1. M14 是 Core 与 Extended 共用的出口

| 范围 | 必须满足 | 不应成为其隐含前置 |
| --- | --- | --- |
| Core 综合验收 | M0–M11 的适用故事、质量/采购通用故事、独立新类型挑战和关键失败恢复；M10 按明确决议验收 | M12 Action、M13 Agent、生产工业连接器 |
| Extended Action | Core 及 M12 的可信授权、模拟远端副作用、幂等/UNKNOWN/回执/结果核验 | Agent 自动调用或物理控制 |
| Extended Agent | Core 及 M13 只读发现/查询/证据/权限/预算合同 | M12 或自然语言自主执行 |

M10 #49 目前要求正式 Release/Activation。它若仍属 Core，缺少可信治理就不能宣称 Core 全部完成。若选择只以本地版本锁作为 Core 出口，维护者须显式缩减 M10/Core 范围并同步 #49/#53；不会靠把 M14 划入 Extended 自动绕过。

### 2. 用三个不同任务验证同一引擎

| 数据集/任务 | 真实动作 | 期望证据与通用性 |
| --- | --- | --- |
| 质量通用化与回归 | 用 M5–M9 通用入口重建异常批次→多工单→订单的等价模型和映射，验证去重、页边界、多路径与断链；另跑旧 M2/M3 回归 | 通用引擎与旧质量结果在同一夹具上对照；保留原用户流程及测试，同一订单不因路径重复累计 |
| 新采购模型 | 新包创建 Supplier/PurchaseOrder/Receipt，自定义字段/主键和关系；完成 Snapshot→Binding→对象/集合→关系→来源 | 不使用固定 10 项制造映射、不增加业务 Controller/枚举/硬编码字段；返回精确模型/绑定/结果范围 |
| 独立挑战 | 测试者在已固定构建之后新增第三领域对象（例如 Facility），使用不同字段名和 PK 类型；再映射、筛选和重开 | 只允许模型/绑定/隔离来源夹具变化；保存前后产品构建 SHA 一致；发现新类型时无需 Java/TS 分支 |

质量和采购两条故事必须都走同一通用引擎，不能仅保留旧固定质量路径、再加采购通用路径就声称多领域复用。第三任务应由未参与实现具体映射的人选择字段和样本；不能预先加一张固定第三业务表然后称“任意领域”。允许通过受控脚本准备隔离 PG 测试数据，必须记录数据变化与产品代码变化的区别。真实生产信息不作为验收输入。

### 3. 所有领域共用的负例和恢复

- **模型与映射**：缺主键、属性类型不兼容、非法枚举/时间、小数精度、重复身份、空值；旧 revision 保存、绑定修改后原执行引用保持固定。
- **来源**：列改名/删除、只读源失联、源结构变化、缺关系端点、来源更新；空集合与 UNKNOWN/PARTIAL/STALE 明确区分，不能自动回落到演示数据。
- **查询**：无效字段/操作符、非 searchable 字段、稳定排序、游标篡改/过期/换查询、预算耗尽、并发数据变化；聚合不以当前页冒充全范围。
- **安全**：本机模式拒绝非 loopback/不合规库配置，页面如实标记无身份；可信模式无凭据/错主体/跨包/撤权拒绝；未来会话模式通过独立会话/CSRF 验收后才纳入。
- **用户流程**：未保存导航、保存冲突保留输入、请求超时核对、刷新/重开、服务重启后版本与绑定保持；键盘/窄屏/错误定位依据 M11 已签收的交互范围。
- **版本和行动**：若纳入正式发行则验证旧批准失效、激活 CAS 和回退兼容；Action 超时不能报告失败可重试或成功，Agent 输出不能自报执行事实。

负例测试应断言实际 HTTP/PG/浏览器行为，不仅断言前端显示一个错误字符串。

### 4. 交付物及责任

| 责任角色（尚未指派具体人） | 交付与签收职责 |
| --- | --- |
| 功能实现者 | 对每个实现 PR 提供用户流程、正反例、受测 SHA 和未测范围，修复回归 |
| 独立技术复核者 | 检查模型/绑定/AST/SQL/来源证据全链路及各领域复用，确认未减少断言 |
| 环境操作者 | 在自己的 Windows 11 既有安装上按 runbook 执行并记录；不覆盖/清理原数据库 |
| 产品/领域用户 | 真实操作并记录完成、误解和恢复；只签实际体验过的范围 |
| 维护者 | 明确 OFIP、Core/Extended 范围与发行决定；CI 绿灯和 PR 合并不代替决定 |

M14 首个交付是一个可复现的 Core 验收包及现有总账对应更新；Extended 两条独立补充。若发现缺口，回到所属 M 的功能 PR 修复，不在验收 PR 塞新运行模块。

### 5. 待决定事项

- 推荐将 M14 标记为“共享验收出口”，而不是 Extended 独有功能；不新增 M15 或另一份产品进度表。
- 确认 M10 的正式发行是否为 Core 必需；决定前维持原 issue 口径，不提前宣告 Core 完成。
- 多领域功能必须正确且有界；当前没有容量 SLO 的证据，不编造生产级延迟/吞吐目标。实现时记录夹具规模、预算和观测值，由维护者批准可复现实验阈值。
- 目标用户和实际执行人尚未指派时保持待办；不能将责任角色写成已经参与验收的真实姓名。

## Compatibility, Deprecation, and Migration Plan

- **产品合同和 Flyway 变更：None。** 不修改 V1–V6，不清库、不改历史 JCS 字节；验收在独立测试数据库进行。
- 保留 M2/M3 固定质量路径作为兼容回归；通用入口替代方案按其功能提案迁移，不能因新采购演示成功删除旧测试。
- 成熟度只在现有产品总账维护；历史报告仍绑定各自 SHA，不批量改写为最新状态。本次设计不会提高任何功能成熟度。
- Native V0.2/本地 query profile、可信 JWT/未来 Session 与本机模式分别列覆盖，未知版本应拒绝而非兼容猜测。
- 失败的验收记录保留原因和后续修复证据；不覆盖原失败记录制造连续成功。

## Test Plan

本提案的**实际**验证只在 PR 中记录文档治理/相对链接检查。以下综合验收均是未来计划，当前 **NOT RUN**：

| 范围 | 命令/真实操作 | 出口证据 |
| --- | --- | --- |
| 文档与合同 | `python -m unittest discover -s doc/tests -p 'test_*.py' -v`；Native 合同变化时运行 `doc/design/tests/test_native_v02.py` | 每套实际数量/状态/受测 SHA，不能当作 Runtime PASS |
| PG/HTTP | 独立 loopback `ontoforge_test_*`、TEST_DB_* 下 `mvn -pl ontoforge-boot -am verify` | JUnit/Flyway、并发/负例、重启保留；不指向开发库 |
| 前端静态 | `npm ci`、`npm run build`、`npm run audit:dependencies` | 真实命令结果；与浏览器分开 |
| 真实 UI E2E | 当前工作流对应的 Chromium→React→Boot→PG，多领域及失败恢复 | 场景名、报告/截图、夹具身份和受测构建 |
| Windows 用户安装/UAT | runbook 的实际启动→新领域建模/绑定/查询→停启→重开；领域用户操作观察 | 操作者和产品签收记录；隔离 CI 不替代 |
| Extended | M12 模拟远端幂等/回执/核验；M13 只读工具/撤权/预算 | 两套独立结果，未选不标 PASS |

选中的必需测试失败、取消或缺报告时不能通过出口；没选中的套件写 NOT SELECTED，环境未运行写 NOT RUN。正式版本发行另有明确发行决定，不由验收包自动触发。

## Rejected Alternatives

1. M14 只有 Extended 才需要：会导致 Core 没有独立综合验收出口。
2. 只添加两个后端业务枚举证明“多领域”：本质仍为固定场景，需要在同一构建后通过全新模型挑战。
3. 将所有 CI 归为“全部通过”：掩盖未选和未运行，也混淆静态检查、浏览器和人工验收。
4. 新建验收平台、报告数据库或第二总账：当前没有对应消费者，以已有 CI/PR/runbook/总账即可形成可审核证据。
5. AI 代签用户验收或把 merge 当正式发布：两者都没有真实操作者和维护者决定，不能作为证据。
