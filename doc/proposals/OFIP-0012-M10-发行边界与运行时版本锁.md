## Motivation

用户已经能够保留本地模型快照；M5–M9 将允许使用这些快照映射测试来源并读取对象。下一步的问题是：选择新版模型时，运行时会不会搭配旧绑定？切回旧模型后，是否仍能解析旧字段？查询翻页期间 Active 发生变化，结果依据哪一版？

M10 #49 的正式发行目标合理，但存在两个需要显式审议的边界：

1. OFIP-0005 已经定义七种治理资源、审批摘要、ReleaseManifest、激活 CAS 和回退。M10 应复用它们，不能另做“快照一键改成 Release”。
2. 当前产品方向允许 `mvp-local` 无登录验证核心价值；该模式的固定本机显示身份没有可信审批权。未来优先复用 yak-ops HttpSession 是规划，当前仍有 JWT 兼容路径；两者都不自动等于已完成发布权限和职责分离。

黄金故事：用户查看一个明确的模型版本和全部绑定版本，服务端检查兼容性；有资格的主体创建正式版本并在一个隔离测试 scope 激活。新查询使用同一组版本，旧查询继续使用自己的固定版本或明确失效。用户回退时重新检查旧组合及当前来源，产生新的事件，历史保持可读。

非目标：本提案不迁移登录组件、不引入完整消费者注册平台、不支持跨包 imports、不更新外部源数据、不把模型回退称为外部 Action 撤销。

## Public Interfaces

### 与 OFIP-0005 的职责分界

正式 `ChangeSet / QualityReport / ReviewDecision / SchemaRelease / Activation` 及其 API 沿用 OFIP-0005 TC04–TC10；须先明确接受适用合同后实施。本文仅新增以下**候选**消费者合同，具体 JSON Schema/TS/Java 与前向迁移在实现 PR 一并交付：

| 合同 | 最少信息与权威 |
| --- | --- |
| `RuntimeVersionLock` | `lockId`、`profileVersion`、`packageId`、互斥 `modelSourceRef`、`modelPayloadSha256`、排序的 `bindingRefs[]`、`lockDigest`、服务端创建时间；由服务端核验后持久保存，不修改内容 |
| `bindingRefs[]` 项 | 沿用本机合同的 `bindingId/revision/digest/sourceId`，以 `kind=OBJECT/LINK` 区分映射并关联 Type/Link 稳定 ID；包含关系查询的全部端点和关系映射，不只根类型 |
| `RuntimeCompatibilityReport` | 精确目标 lockDigest、检查 profile、源结构指纹、checkedAt、结构/类型/主键/基数/分类风险；限定组合的 `bindingCompatibility=COMPATIBLE / INCOMPATIBLE / UNKNOWN`；外部 `consumerImpactStatus` 单列，附问题码和适用范围 |
| `RuntimeSelection` | 对一个测试 scope 选择 lockId、`expectedRevision`、reason、idempotencyKey；本机模式只称本地运行组合选择，不产生可信正式 Activation |

`modelSourceRef` 在 M10 前只允许已核验的 `LOCAL_SNAPSHOT(snapshotId)`；不把可变 Draft 用作持久执行依据。正式模式仅在 M10/OFIP-0005 决议后扩展为 `SCHEMA_RELEASE(releaseId)`，同时核验 ReleaseManifest 与审批链。对象身份不包含 lockId；版本锁决定读取合同，不能为同一对象生成新身份。

M7 响应中的 `versionLock` 是该 execution 的内联读取依据；这里的 `RuntimeVersionLock` 是可重开的持久组合资源，不替代 M7 合同。执行时服务端把此资源展开为 M7 的 `typeSourceRef/payloadSha256/bindingVersions/sourceSchemaFingerprints`，逐项核验相同的 `bindingId/revision/digest/sourceId`；引用 lockId 也不能省去执行证据。本机 revision 不冒充 Native BindingVersion 的 SemVer，未来适配必须显式版本化；新增正式来源时旧客户端应拒绝未知判别值。

摘要必须有明确 profile、字段排序和域分离；`modelPayloadSha256` 沿用快照的裸 64 位小写 hex，而 Native V0.2 的 `schemaReleaseDigest` 等字段要求 `sha256:` 前缀。**加前缀不是将快照升级为正式发行**；只有实际存在且验证成功的 Release 才能填正式发行字段。

API 候选在既有安全域 `/api/model/runtime-locks` 提供创建、按 ID 读取、兼容检查和 scope 当前选择；正式发布/激活复用 OFIP-0005 路径，不新增同义路由。创建需要相应包的写权限，读取需要当前包读权限；这些运行时操作权限需在实现时显式扩展，现有 B0 的五个操作不能假称已经覆盖。

| HTTP / 业务码候选 | 行为 |
| --- | --- |
| 400 `MALFORMED_VERSION_LOCK` | 来源类型混用、未知字段、重复 bindingRef 或无效引用 |
| 401 `AUTHENTICATION_REQUIRED` / 403 `ACCESS_DENIED` | 可信模式使用当前认证及服务端资源授权；所有 by-key/报告读取同样受控 |
| 404 `VERSION_LOCK_NOT_FOUND` | 有权上下文中未找到锁 |
| 409 `RUNTIME_SELECTION_CONFLICT` / `IDEMPOTENCY_CONFLICT` | 旧 revision 或同 key 不同请求，不覆盖 |
| 412 `COMPATIBILITY_EVIDENCE_STALE` | 源结构/目标 lock 或检查 profile 改变，重新检查 |
| 422 `RUNTIME_INCOMPATIBLE` / `GOVERNANCE_REQUIRED` | 该组合 bindingCompatibility 不兼容/未知不能选择；本机无可信身份不能正式发布 |
| 503 `PERSISTENCE_UNAVAILABLE` | 无法判定提交结果时保留原 key 查询，不伪报失败已回滚 |

## Proposed Changes

### 1. 先明确 M10 完成口径

| 待决定事项 | 建议与后果 |
| --- | --- |
| 本机核心优先如何与正式发行共存 | 先做 M10-A 本地不可变版本锁与兼容检查，名称明确为本地；M10-B 正式发行、激活及回退遵循 OFIP-0005 和可信授权前置条件 |
| M10 是否仍属 Core 必须完成 | **按 issue 当前口径，M10-B 未验收则 Core 含正式发行的目标未完成**。若维护者希望 Core 仅要求 M10-A，必须明确缩减范围并同步 #49/#53；本文不自动降低标准 |
| 登录路线 | 不把 JWT 接入变成本机 M5–M11 前置；未来 HttpSession 适配独立设计，验证 Cookie/CSRF/会话过期/撤销及现有 JWT 兼容，不在 M10 偷换认证体系 |
| 既有 OFIP-0005 | 正式治理只维护该提案的资源/状态权威；本提案是运行时消费补充，不宣称替代或接受它 |

M4 不在本轮评审范围；实现方只消费其最终接受的类型来源合同。M5–M9 以本地快照工作，避免“先查询才能发布、先发布才能查询”的依赖环。

### 2. 读取和选择的一致性

1. 用户选择模型来源及各绑定不可变版本；服务端推导 packageId 和完整引用闭包，拒绝跨包/跨源及缺失端点。
2. 服务端从真实快照/发行读取规范化内容并核验摘要，对绑定做结构、主键、类型、分类和关系端点检查；保存锁内容及摘要。
3. 兼容报告绑定**确切**锁与源结构指纹。不把结构 Diff、预览样本通过或消费者列表为空称为全面兼容；没有注册消费者时延用 `UNKNOWN_CONSUMER_IMPACT` 等诚实结果。限定本机组合的 bindingCompatibility 可在完整验证后为 COMPATIBLE，而外部 consumerImpactStatus 仍为 UNKNOWN_CONSUMER_IMPACT；两者不是同一判断。本机选择不因未建设外部消费者目录而永远阻断，也不能扩大保证；正式治理另按 OFIP-0005 的风险/审批 Gate 判断。
4. 本机选择在一个 PG 事务内写入选择历史和 scope 指针，CAS 单调 revision；保存失败不改变当前指针。正式 Activation 仍使用 OFIP-0005 事件和授权合同。
5. 查询开始只解析一次当前选择并锁定所有模型/绑定引用，执行成功后消费 M7 的有界物化 `resultSnapshotRef`。后续页验证原 lock、queryDigest、当前授权、来源可用性与依赖结构，读取同一结果快照；源普通增删改不得重算旧页成员、值或计数，激活变化不得让同一查询中途换版本。已锁定旧版本仍合法时可继续，TTL/重启、来源结构漂移或授权撤销则失效，不因存在游标而放行。
6. 模型/绑定锁不冻结业务事实。即便旧模型一直可读，源列删除、数据改变或来源不可用仍可使执行失败；M9 的来源时效/一致性语义持续适用。

### 3. 正式版本与回退

按 OFIP-0005 的审批摘要和职责分离创建不可变正式版本。当前 DraftValidation 固定生成 payload `version=0.1.0`，因此必须对 TC-D8 明确选择：保留历史字节并使用独立 ReleaseManifest 发行版本，或创建新候选重新摘要/受审；不能改旧 JSON 后沿用摘要。

SchemaRelease 激活只切模型控制面。运行时版本锁/选择另有 revision 和报告，不自动随模型激活升级所有 Binding。UI 同时显示“正式模型当前版本”和“本次查询实际版本组合”，避免宣称二者已经共同切换。

从 M5 本地快照 Binding 进入正式来源时，不能只在根 TypeRef 换 releaseId：M7 原有类型来源与 Binding 来源必须精确一致。M10-B 须显式接受新版 Binding/TypeSource 合同，由用户复核生成指向 `SCHEMA_RELEASE(releaseId)` 的**新对象 Binding 修订**，再生成同一 Release 下全部 LinkBinding 和端点引用闭包的新修订；原本地修订/摘要保持不变。键语义和稳定类型 ID 不变时保留 identityDomainId，键语义改变则按 M5/M6 创建新身份域并报告不兼容。全部新引用验证完成才创建正式 RuntimeVersionLock，再显式选择；不能将 payload 相同当作来源身份相同或静默适配。实现测试须覆盖 Snapshot→Release 成功迁移、混用两种来源拒绝及保留旧本地查询。

回退是一次新的选择/Activation，重新核验当前权限、旧锁完整性、旧 Binding 和**当前**源兼容；不可用时拒绝，不只恢复一个旧 releaseId。不得删除新版本、擦除历史或倒转业务源/外部副作用。

### 4. 实施切片

M10-A 一个可操作 PR：查看/创建版本锁 → 真实兼容检查 → 选择并按该组合查询 → 两版本切换和失败恢复，含 Java/PG/React/Chromium。

M10-B 在治理及身份合同明确接受后，沿用 OFIP-0005 B1 正式发行和 B2 激活/回退纵向切片；每片独立可操作。不能以“一个 M 一个 PR”强行把身份移植、审批、发行和运行时迁移堆入巨型 PR，也不能只交无调用接口。

## Compatibility, Deprecation, and Migration Plan

- 本次仅提案，不修改 Native V0.2 Schema、Java/API、PG 或现有认证。实施使用当时下一个未占用的前向 Flyway 版本；当前 V1–V6 均已存在，不能使用 OFIP-0005 历史建议的 V4。
- 既有 Draft、本地快照、原 JCS 字节和摘要保持不变；历史 `mvp_demo_binding` 不自动转为通用正式 Binding。显式映射/校验后创建新版本，保留 M2/M3 回归入口。
- 新 `SCHEMA_RELEASE` 来源是判别联合的显式扩展，旧客户端遇到未知来源必须拒绝，不能当作 `LOCAL_SNAPSHOT`。正式 Native V0.2 query/result 适配另有字段语义审查，不滥用 release/index/auth 字段。
- 不删除旧版本锁或被证据引用的绑定；归档与保留期限待实际容量需要再提，不预建 GC/消费者平台。
- 迁移失败停止启动或回滚当前事务，不 repair、不清库。恢复应用旧版本前检查前向迁移兼容范围，不能通过改 Flyway checksum 倒退。

## Rejected Alternatives

1. 快照直接标记 PUBLISHED：缺少可信审批、发行坐标和权限证据，破坏 OFIP-0003/0005 边界。
2. 同时激活模型、绑定、索引但不锁版本：会把多种权威混为一个状态，当前也没有 Index 子系统，拒绝。
3. 用无登录本机显示身份担任审批人：它没有受信主体证明，无法形成正式审查证据。
4. 为 M10 重写登录、审核和发行平台：重复 OFIP-0005，与核心优先方向冲突；保留已有路径并按独立决定适配。
5. 回退时跳过来源检查或覆盖历史：旧模型可读不表示旧来源仍可执行，外部副作用也无法被指针回退撤销。
