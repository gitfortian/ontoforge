## 0. 执行摘要：唯一产品骨架

我们的本体产品不是 OWL/RDF 编辑器的封装，不是图可视化工具，也不是简单的通用 ETL。它为企业分散在 ERP、MES、QMS、PLM、WMS、EAM、设备时序、文档和应用中的对象、事实、关系、规则和操作能力构建**可信且受治理的语义运营层**。

核心问题是：**是什么？与什么有关？何时发生什么事实？根据哪个知识与规则版本形成什么判断？谁允许做什么？实际做了什么，结果是否经业务核验，能否重建当时的过程？**

**顶层不可违反的不变量**：能够从公理或规则推导一个结论，不等于业务主体被授权执行命令；外部接口响应成功，也不等于目标业务状态已经达成。

统一采用以下产品/架构原则（待签收）：

1. **Native Ontology Schema / Typed AST 是模型定义和发布权威**。ObjectType、Property、LinkType、DataBinding、ObjectSet、Rule、Function、DecisionStrategy、Policy、Action 是一等资产；OWL/RDF/SHACL/SPARQL 按独立语义 Profile 适配，不能控制 Native 核心发布与行动。
2. **模型定义、业务实例、数据绑定、对象投影、查询、决策、授权、执行与审计分离**。ERP/MES/QMS 对各自业务事实负责，本体对象/关系索引是有来源/版本/撤权政策的可重建读模型。
3. **ObjectSet 是类型化、Lazy、可组合的逻辑查询与授权合同**，不能退化成 Java 内存 List 或绑定单一 SQL/图引擎；在多跳、聚合及分页中显式管理身份去重、权限、来源、时间、预算和结果质量。
4. **Function/Decision 不具有隐式副作用**；EDIT_PLAN 仅产生拟议 ChangeSet，Action 通过独立 Policy、审批、版本/EffectScope 锁定、Outbox、远端回执与业务状态核验建立可信闭环。
5. **P0 从模块化单体、Java 21 / Spring Boot 和 PostgreSQL 默认基础方案起步**。PG17.11 的指定 ObjectSet 与 Action Outbox POC 已真实运行；搜索/图/专业语义/时序/复杂消息系统按负载和业务 ROI 引入，不一开始复制 Palantir 的分布式服务规模。
6. **制造质量异常 → 跨系统订单影响 → 受控冻结或复检**是第一条端到端黄金故事；设备维护及客户术语同名异义与撤权为补充故事。每个开发 PR 都要有独立可见、可重复的实际交付。

以上为**路线收口建议**。当前仍不能宣称真实生产 ABAC、亿级对象 SLA、跨系统 Exactly Once、真实工业 ERP 安全写回与可严格回放外部物理行为。

## 1. 产品使命、用户与非目标

### 1.1 应用价值

大型制造企业的业务系统各自理解部分业务事实：QMS 知道质量结果，MES 知道工单和生产批次，ERP 知道订单及库存，EAM 知道设备维修，PLM 知道产品工艺。Agent 仅凭文本和检索结果无法保证稳定的同一对象身份、关系证据、规则版本、事实新鲜度或行动许可。

产品提供一个独立于特定业务系统和模型厂商的语义执行基础层，允许员工、业务应用、Agent 安全地查询企业对象、分析可追溯影响、解释确定性决策，并通过原业务系统接口执行明确授权的业务动作。

### 1.2 角色与任务

| 角色 | 主要工作 | 核心交付 |
|---|---|---|
| 企业架构师/领域专家 | 建立业务对象、关系、模型包、术语 | Studio、Native Package、Registry、Review |
| 质量/生产/供应链专家 | 校验业务语义、规则、影响链和业务处置 | Rule、Decision、业务场景、审批 |
| 集成/数据工程师 | 接源、映射字段、认定对象身份、追踪漂移 | Connection、Binding、Identity、对账 |
| 应用/Agent 开发者 | 消费受限对象、决策和可调用能力 | SDK/MCP、ObjectSet、Function、Capability |
| 一线用户 | 查对象、看影响、申请受控处置 | 对象详情、查询、行动中心 |
| 安全/运维人员 | 审批、权限、审计、故障、质量监控 | Policy、Evidence、Observability、Ops |

### 1.3 明确非目标

不取代 ERP/MES/QMS/PLM；不要求业务源数据全量复制、不要求全部语义资产统一转换为 OWL；不把图谱展示当成真实业务能力；不将 LLM 输出当成事实或授权；P0 不自动控制 PLC/DCS/SIS；不推测 Palantir 非公开存储/微服务协议；不能因参考 GB/T/OMBOK 就宣称符合全部国标；不基于 POC 数字承诺生产 SLA。

### 1.4 四级领域模型包

L1 **Ontology Core**：ObjectType、LinkType、Binding、ObjectSet、Rule、Decision、Policy、Action 等；L2 **Manufacturing Foundation**：工厂、组织、物料、批次、订单、工单、设备、业务时间；L3 **Domain Pack**：质量、BOM、供应链、设备维护等；L4 **Enterprise Extension**：具体工厂术语、源绑定、规则和身份策略。模型依赖锁、命名空间和兼容检查必须防止下游直接覆写上游定义。

标准文档本体应是可选专业 Profile；不能把章、条、信息单元强制加入所有工业对象的基础类型。

### 2.1 统一页面信息架构和用户流程

建议导航：**工作台 → 本体设计 → 连接与映射 → 业务对象 → 查询与分析 → 决策与行动 → 语义协同 → 平台管理**。产品设计以用户任务而非“专业工具菜单”组织。

主流程：选择制造领域包/创建模型 → 定义类型与 Link → 校验/草稿 → ChangeSet 审查 → 不可变发布 → Connection 与 Data Binding → 来源/身份核验 → Object/Link Index → ObjectSet 查询 → Function/Decision → Policy/审批 → Action → 结果核验/对账。

**阶段纪律**：P0 只需真实交付建模→校验→保存→审核→发布→版本读取；不能为了让首页漂亮而伪造 P1 尚未创建的物理对象或 P3 尚未执行的业务状态。

**逻辑职责**首先在模块化单体中体现，不直接映射为独立部署单元。身份、权限、状态及版本在各层有不同权威和发布 Gate。

| 限界上下文 | 拥有的事实/合同 | 严禁越界 |
|---|---|---|
| Native Model / Compiler | 类型、属性、关系、Schema AST、Ref 检查 | 把本体定义当成业务实例 |
| Registry / Release | Draft、ChangeSet、质量报告、审批与不可变 Release | 只因定义通过就自动激活数据/Action |
| Connection / Binding | 来源、字段/链接映射、属性权威、身份、Checkpoints | 将源凭证写入可分发 DSL 包 |
| Object Runtime / Query | 可重建对象/关系索引、Typed ObjectSet、查询结果 | 接受任意客户端 SQL 和自填管理员权限 |
| Function / Decision | 确定性规则计算、函数、推荐行动意图 | 绕开 Action 直接操作 ERP |
| Action Runtime | 审批、Policy、Outbox、执行状态、回执/核验 | 用 HTTP 200 宣称业务已达成 |
| Security / Evidence | 统一授权、衍生数据标签、审计证据和撤权 | 只在前端隐藏无权数据 |
| Standard Adapter | 有 Profile 的语义标准导入导出和 Loss Report | 充当第二套模型发布权威 |

### 3.1 工程技术选择及引入时机

| 领域 | P0 默认/候选 | 工程取舍 |
|---|---|---|
| 服务框架 | Java 21 + Spring Boot | 候选，需经 S0 依赖/实际启动验证 |
| 架构 | 模块化单体 + Ports & Adapters | 逻辑分层，按隔离与规模再拆服务 |
| 模型/发布/对象与关系/Outbox | **PostgreSQL** | 真实 PG17 POC 支持 P0 可行性；容量/高并发未签收 |
| 前端 | React + TypeScript 候选 | 围绕业务旅程交付，不因脚手架风格损失产品统一性 |
| Graph / Search | PostgreSQL 索引优先；专业图/搜索按 POC | 保留 Query Adapter，避免强行锁死物理实现 |
| 标准语义 | Apache Jena、RDF/OWL/SHACL/SPARQL 可选 | 不强制成为 Native Runtime、并非必装 |
| 设备时序/文件 | 外部 Historian、数据引用；S3/MinIO 视需求 | 不强制全量复制为知识图谱 |
| 消息/缓存/工作流 | Postgres Outbox 基础；Kafka/Redis/Temporal 等按需 | 不能拿中间件数量替代一致性协议 |
| 认证策略 | OIDC/OAuth2 + 服务端 PEP/PDP，OPA 候选 | Session GUC POC 不是可直接生产使用的 ABAC |
| 可观测 | OpenTelemetry / Trace / Metrics / Audit | 可观测来源滞后、查询成本、执行 UNKNOWN |
| 工程复用 | Yak Ops 可选择性裁剪 | 许可、代码、安全、依赖需先审查，未默认采用 |

Dev 为主服务 + PostgreSQL + Mock 源；Pilot 加受控 QMS/MES/ERP 接口；生产才根据多工厂/网络与容量扩容。**部署 Kubernetes 不自动实现高可用、跨系统事务或审计合规**。

## 4. Native 元模型、Typed AST 与发布权威

### 4.1 五个机器合同平面

本项目配套权威技术合同为 [Native DSL/AST V0.2](./design/核心本体元模型与Native-DSL-AST契约_v0.2.md)，其五份 Draft 2020-12 JSON Schema 与制造质量样例是当前可执行结构参考：

| 合同 | 核心内容 | 绝不等同于 |
|---|---|---|
| Native Package | ObjectType、Property、LinkType、Binding、Function/Action 等声明 | 已经存在 ObjectInstance |
| Normalized Typed AST | 编译节点、依赖 Ref、版本化结构 | 已审批/已激活 Schema Release |
| ObjectSet Query | Filter/Traverse/Aggregate/Sort/Page、预算 | 已有授权或任意原生 SQL |
| ObjectSet Result | Accuracy/Completeness/Freshness/Scope/Checkpoint | 企业事实全量实时正确 |
| Semantic Execution Record | 模型/规则/决策/授权/行动/回执/Outcome 证据 | 客户端伪造的可执行命令 |

Native 对象类型具有稳定 id、apiName、primaryKeyRef、属性定义；LinkType/LinkFact、ObjectType/ObjectInstance、Required/FactCompleteness 必须区分。模型定义拥有稳定业务身份与兼容性规则，不必须生成 HTTP IRI 才能保存/发布。

示例结构测试中的 SHA256 字符串仅为格式占位符。真正的 Canonical JSON（如 RFC 8785/JCS Profile）、锁文件、ReleaseDigest、SourceMap、签名和发布审批验证必须在正式 P0 编译器与 Registry 中实施，不能将 JSON Schema 有效直接视为可信发布。

### 4.2 版本化发布生命周期

~~~mermaid
flowchart LR
  Draft --> Validate --> Review --> Approved --> ImmutableRelease --> Activation
  Review --> Rejected --> Draft
  Activation --> Deprecate
~~~

- Draft、ChangeSet、ReviewDecision、QualityReport、Release、Activation 分别保存；审批绑定内容摘要与依赖锁，修改后旧审批自动失效。
- SchemaRelease、BindingVersion、Indexer Build/Activation、FunctionRelease、ActionDefinition 和 PolicyVersion 独立生命周期；模型升级不能自动写回业务对象、改外部系统或迁移所有投影。
- 主键、LinkType、分类/授权、依赖、可查询性变化必须出具 Compatibility Report；发布失败不激活半成品；回滚不能删除外部副作用事实。
- 包与命名空间受组织/工作空间 ACL 约束；跨来源实体对齐与行业包复用要按受审映射，而不是按中文/英文同名字符串推测实体相同。

### 4.3 OWL-first 历史迁移

V0.1 的 EntityType/DataProperty/ObjectProperty/IRI、DisjointClasses 等不等于 Native V0.2 的全部运行语义。迁移必须使用 [V0.1→Native V0.2 迁移矩阵](./design/V0.1到NativeV0.2迁移矩阵.md)，对每个标识、域/范围、公理和来源给出 LOSSLESS/PARTIAL/UNSUPPORTED；没有对应 Profile 不得声称无损。保留 V0.1 JSON Schema/样例作为**遗留兼容测试夹具**，而不是当前模型研发依据。原版本的审批不得自动转移给新 Native Release。

## 5. Data Binding、身份与双系统状态

### 5.1 源、投影与外部回执各有权威

企业系统是其主营业务事实的权威来源，本体系统不必每次查询都实时打 ERP/MES/QMS，也不应一股脑复制全部数据。优先使用 **本地对象/关系投影 + 适当增量同步 + 按需联邦查询/外部引用** 的混合模式。

| 事实或状态 | 谁是权威 | 必须维护 |
|---|---|---|
| SourceFact | ERP/MES/QMS 等源系统 | 来源、版本、ObservedAt/EffectiveAt、Checkpoint、授权 |
| BindingDefinition | 本体平台模型/映射管理 | PropertyRef/SourceField/Authority、来源 SchemaVersion、IdentityRule |
| Object/Link Index | 本体平台可重建读投影 | IndexGeneration、SourceWatermark、失效/撤权 |
| OperationalEdit | 本体平台经核实的运营编辑/意图 | 审批、版本、状态、冲突范围 |
| EffectiveObjectView | 查询时按权威与规则形成 | 已知/未知、冲突、过期与来源证据 |
| ExternalReceipt/Outcome | 远端回执 + 已确认的业务状态 | remoteId、IdempotencyKey、执行/核验差异 |

**源事实同步一致性**与**本体发起 Action 后的业务结果一致性**是两个不同问题，不能用一个 status 字段概括。ERP 已冻结订单而本地仍显示旧状态时，应告知用户索引水位滞后；Action 已提交但远端未知时，只能显示 UNKNOWN。

### 5.2 属性级来源权威与身份

- Property FieldMapping 声明 AUTHORITATIVE 或 SUPPLEMENTAL；不能因为 MES 主要维护 ProductLot 就认为它对 ERP 订单金额也有权威。
- SOURCE_KEY 只是来源内身份；APPROVED_CROSS_SOURCE 必须有审定证据和冲突政策；同名同键不能自动 owl:sameAs，也不能直接生成 LinkFact。
- 必填字段的结构约束不等于事实完整；来源缺失、不可靠、撤权、冲突或过期时结果可为 UNKNOWN/PARTIAL/CONFLICTED/UNAUTHORIZED，不能把未知当 False。
- 源 Schema 漂移、重复投影、乱序更新、来源撤权/恢复需审阅、增量对账与重建；本地事实与外部已批准编辑冲突时，必须显示冲突而非静默覆盖。


## 6. ObjectSet Query Runtime：权限、查询预算和结果证据

### 6.1 逻辑查询合同

ObjectSet 代表在某模型版本、来源快照与权限范围下可计算的业务对象集合，并不等于 Java 内存数组、图数据库中一组永久固定顶点或简单 SQL 脚本。查询入口以 Typed AST 组合 Filter/Search、Traverse/Join、Project、Sort/Page、Aggregate 和 Explain。

- ObjectSetDefinition、动态 QuerySpec、静态对象 ID 集合、临时句柄和执行结果快照分属不同资源。不能因为它们都叫 ObjectSet 就使用相同版本/生命周期。
- Filter 必须验证 Property 的类型、可检索性和运算符；Traverse 验证 LinkType 的源、目标、方向与最大深度；Aggregate 依赖真正的授权、对象身份和精度声明。
- 金额计算先按最终 CustomerOrder **业务对象身份去重**，不能将重复关系路径造成的重复行错误统计为重复订单。
- 所有查询必须有超时、访问对象数、深度、行数/聚合成本、Query Explain 与执行预算；即使 LIMIT 25，也可能先执行数百万 Link 的 Join、DISTINCT 和 Sort。
- 不接受客户端 raw SQL、自行传入的 role=admin/authorizationContext 或不经授权的执行计划。授权要下推到对象、Link、属性、聚合中间结果与派生数据。

### 6.2 QueryResult 不能混淆的质量维度

| 维度 | 主要取值 | 工程与 Agent 含义 |
|---|---|---|
| **Accuracy** | EXACT / APPROXIMATE / UNKNOWN | 结果是否精确、近似是否提供误差界限 |
| **Completeness** | COMPLETE / PARTIAL / UNKNOWN | 结果覆盖的是整个合法请求范围还是已知子集 |
| **Freshness** | FRESH / STALE / UNKNOWN | 源同步和索引时点是否满足该业务的时效政策 |
| **AnswerScope** | REQUESTED_SCOPE / KNOWN_SUBSET | 只在已知子集中正确的数不能被声称为全量总数 |
| **Error** | 结构化安全错误、无伪造聚合值 | 运行失败不是“没有数据”也不是总数为 0 |

SOURCE_PARTIAL 时得到 COUNT_DISTINCT=17 可以是**已知子集的准确计数**，但不能由此推出业务世界只有 17 条影响订单。不能将聚合的近似误差与来源缺失问题混为一个百分比。

## 7. Rule、Function、Decision Strategy：计算和行动隔离

| 资产 | 输入、版本和输出 | 必须拒绝的误用 |
|---|---|---|
| RuleDefinition | 确定性业务规则，Rule Artifact/Version 与作用条件 | 因规则存在就声称来源事实完整 |
| FunctionDefinition | READ_ONLY 或 EDIT_PLAN、签名、输入输出、实现摘要、预算 | READ_ONLY 产生 ChangeSet、直接写 ERP |
| DecisionStrategy | 明确引用 Rule + READ_ONLY Function、事实和运行版本、业务 Outcome 类别 | 决策结果自动当作 Action 权限 |
| PolicyDefinition | DATA_ACCESS / ACTION_AUTHORIZATION / APPROVAL、Policy Artifact/Version | 存在 Policy 定义就代表 PERMIT |
| ActionDefinition | 目标 ObjectType、作用范围、EditPlan、策略、审批、执行器、幂等/核验 | Action 定义就是实际执行授权或成功事实 |

业务 Rule、业务 Strategy、Type/Schema、Policy 和确定性 Function 本来就是企业的语义资产；**不能为了形式统一强迫它们全部转换为 OWL 公理**。专业 OWL 推理可以生成可追溯的事实建议，但不能绕过来源证据、DecisionStrategy、Action Policy。

Agent 的上下文采用 Schema → ObjectSet / Entity / Link → SourceEvidence / State → Authorized Capability 分层提供。Function 的实现 Digest 或 EffectScope 变化意味着旧 Action 的授权和审批必须失效；不能自动升级底层函数后继续复用曾签收的风险范围。

## 8. Action Runtime：受控业务执行和故障恢复

### 8.1 建议的业务执行闭环

~~~mermaid
stateDiagram-v2
  [*] --> Proposed
  Proposed --> Denied: policy or evidence reject
  Proposed --> PendingApproval: human approval required
  PendingApproval --> Approved: approval bound to versions
  PendingApproval --> Denied: expired or denied
  Approved --> Queued: validate scope and source revision
  Queued --> Dispatching: transactional outbox claim
  Queued --> Blocked: drift / authorization revoked
  Dispatching --> Unknown: timeout or uncertain side effect
  Dispatching --> ReceiptConfirmed: durable remote receipt
  ReceiptConfirmed --> VerifiedSuccess: confirmed business outcome
  ReceiptConfirmed --> Unknown: business state cannot be verified
  Unknown --> ReceiptConfirmed: reconcile accepted receipt
  Unknown --> Failed: authoritative rejection
~~~

**这是一张目标逻辑状态图**，不是已实现的生产 API；V0.2 Record、POC 实验枚举和未来 Action API 必须在 P3 前统一映射。实际运行时不应依赖“前端画出流程”就判断业务已执行。

### 8.2 核心执行不变量

1. Preview 默认**没有外部真实副作用**。若函数预演会调用不可隔离的写接口，应拒绝预演或强制使用模拟沙箱。PreviewDigest 绑定目标、对象状态、规则、版本及范围。
2. APPROVED 不等于可立即执行。派单前重新检查授权、SourceRevision、Schema/Binding/Function/Decision/Policy/Action 版本、EffectScope 和审批有效期。HIGH/CRITICAL 必须人工审批。
3. ActionAttempt 与 Outbox 进入**同一个 PostgreSQL 事务**。Worker 通过 SKIP LOCKED、Lease 和 ClaimToken 竞争领取，同目标业务动作根据 Scope 执行冲突仲裁。
4. 同一 IdempotencyKey + 完全相同 Payload 才能安全复用；不同 Key 同时修改同一目标仍可能冲突。Worker 失去 Lease/Token 后不得再覆盖新 Worker 的本地执行状态。
5. 远端接受后网络断开/本地崩溃会进入 UNKNOWN，**不等于业务失败**；优先查询幂等回执对账，若外部系统没有稳定回执/幂等保证则保守停止自动重发并转人工处理。
6. ExternalReceipt=ACCEPTED 只代表接收/持久化回执；必须独立进行 OutcomeVerification 才能声明业务变更已生效。原业务状态追平显示 SOURCE_CAUGHT_UP，源事实反向变化显示 CONFLICTED/UNKNOWN。
7. 本地 ClaimToken 无法撤销已经发送给远端的 HTTP 命令；跨 ERP、PostgreSQL、MES **没有可以假定的 Exactly Once 原子事务**，仍需幂等、核验、补偿及人工恢复。
8. Schema 回滚不意味着 ERP 已执行的实际副作用被逆向恢复；Action 需要自己的补偿业务语义和审计证据。

### 8.3 已实测 / 尚未实测

PR #8/#9 的 MockERP 是真实独立 HTTP 进程和独立持久数据库。用例涵盖：Worker 领取后请求前进程崩溃、远端确认后本地未记账崩溃、回执断线、12 并发相同 IdempotencyKey、不同 Key 相同业务目标排他、租约过期/被盗领及旧 Worker 迟到错误。两组高扇出矩阵各通过基础 14 + 强化 16 项。

**限制**：模拟 ERP 自行保证幂等及回执查询，不代表真实 ERP/MES/QMS 都支持；即使 MockERP 确认，也不是工厂真实物理业务已完成。生产开发前必须与具体业务系统签署幂等/状态/重试合同并测试真实沙箱。

### 8.4 Semantic Execution Record

这是服务端生成、不可用客户端提交 JSON 伪造的执行证据合同，关联：

- Knowledge：SchemaReleaseDigest、BindingVersion、IndexSnapshot、SourceCheckpoint、事实/时态完整性。
- Decision：Rule/Function/DecisionStrategy/Policy/Action 的**联合版本和实现摘要**、输入与计算/策略结果。
- Authorization：调用主体、Policy 评估、审批人、审批时刻、EffectScope。
- Intent：目标对象、操作、预演摘要、源预期版本、幂等键。
- Execution：Outbox、Worker、远端命令 ID、接收回执、未知态、重试、错误。
- Outcome：业务状态核验、来源追平/冲突、人工处理和审计时间线。

**历史可重建不等于可以严格重新执行出相同的物理结果**，尤其当涉及 LLM、外部 ERP、人员审批和真实设备。系统应保存当时的输入、版本、可观察结果、不可确定性和证据引用，不重放不可逆工业操作。

## 9. 企业安全、权限传播与可运营性

### 9.1 服务端可信边界

身份从可信 IAM/OIDC/OAuth2、工作空间和执行主体建立，不接受客户端自己指定“admin”。建议最小区分 ViewSchema、ViewInstance、ReadProperty、TraverseLink、CallFunction、PreviewAction、ApplyAction、ApproveAction、AdminConnector。

- 定义权限、对象行/属性列/关系边、业务来源、动态过滤与聚合中间结果、Function、SDK/MCP、Agent Context、Action 参数和执行器权限**分层实施**。
- 来源撤权、模型版本替换、工作空间角色变化必须让后续查询、游标、缓存、派生输出、索引投影、Embedding 等及时失效；定义明确的撤权传播时限及例外拒绝策略。
- Row/Column 读时过滤**不等于**导出、缓存、Function 返回、Agent 摘要等派生数据的强制访问标签传播；派生数据必须携带安全分类/来源与保留规则，避免从计数、错误消息、聚合或查询计划泄漏受限对象存在性。
- PostgreSQL RLS 可以作为纵深防御；**POC 使用可信 session 的 GUC/角色模拟**，绝不允许面向不可信用户开放任意修改 GUC 的数据库直连以伪造租户身份。
- 对高风险 Action 必须再次核验当前主体、来源事实、模型版本与审批；授权服务不可用时按风险 Fail Closed，不能用已缓存的 Agent 文本继续执行。

### 9.2 发布、数据和运维的各自一致性

Schema Release、Binding Activation、IndexBuild 与 ActionFunction/Policy 的部署、审批和激活是分开的变更流程。Schema 发布是模型控制面事务；索引可按 Snapshot/Watermark 重建；外部 ERP 写回是跨系统受控业务流程，不能把其失败当成普通数据库回滚。

研发和试点必须有发布审计、回滚及缓存失效、失败恢复、查询成本和时效监控、Action UNKNOWN 告警、审计保留、备份与恢复演练；RTO/RPO、冷热容量、p95/p99、撤权延迟要由正式试点数据确定，不借用营销数字。

## 10. 开放标准与知识工程：专业互操作而非第二真相源

Palantir 的 Ontology Language、ObjectSet、Function、Action、Security 是**对标产品抽象**；我们不宣称掌握其非公开代码或物理拓扑。研究来源保留于 [Palantir 官方研究](./research/2026-10-15-Palantir-Ontology-运营核心深度研究.md)。

- **OWL/RDF/SPARQL**：在限定 Profile 内表达/交换类、属性、公理与事实视图，不负责业务执行或企业 Connector 凭证。
- **SHACL**：为 RDF 模型提供质量约束能力，不代替 Native Schema/发布兼容、业务审批或 Action Policy。
- **标准适配**：按支持子集生成 LOSSLESS_SUPPORTED / PARTIAL_SUPPORTED / UNSUPPORTED / ERROR 报告，不能静默丢弃历史 IRI、DisjointClasses/EquivalentClasses 或业务效果范围；适配后的 RDF 改动只能变成 Native ChangeSet 候选。
- **GB/T 48000.3—2026**：已研究标准数字化中的标准本体建模要求，通用本体仅复用可适用原则，特定章/条/信息单元归独立 Standard Document Ontology Profile。参见 [条款差距矩阵](./research/2026-10-14-GBT48000.3-本体建模要求差距矩阵.md)。尚未完成标准 Profile 实现与符合性测试，不得宣称通过国标。
- **GB/T 48000.4—2026 和 OMBOK**：采纳语义共识、审核、知识质量和治理启发，不把标准制定审批流程强制变成所有工厂的通用流程。参见 [研究差距报告](./research/2026-10-14-OMBOK-GBT48000.4-蒸馏与差距分析.md)。

## 11. 工业黄金故事与负例

### 11.1 主故事：质量异常批次 → 影响订单 → 受控处置

QMS 的 QualityEvent 指向有证据的 MaterialLot；MES 维护 ProductLot/WorkOrder 的身份与使用关系；ERP 维护 CustomerOrder/履约状态。Binding/Identity 审批及对象关系索引建立可查询路径；ObjectSet 从 HELD 质量事件过滤，经多跳 LinkFact 查受影响订单，按授权和对象身份去重聚合数量/金额；READ_ONLY Function/Decision 输出有版本的风险建议；Action 经 Policy、审批与新鲜事实复核后在受控 QMS/ERP 沙箱执行冻结或创建复检任务，并通过回执/业务状态核验和审计闭环。

必须覆盖拒绝用例：同名但业务含义不同不自动合并、没有来源关系不能生成 LinkFact、撤权字段不能经聚合泄漏、来源不完整不能编造全量结果、Function 不能直接写 ERP、来源版本/审批过期必须重审、外部超时 UNKNOWN 不得声称成功。

### 11.2 第二故事：设备异常 → 维护计划

Equipment、SensorRef、Observation/Alarm、WorkOrder、MaintenancePlan 以对象与时态来源组织；高频设备数据仍从 Historian 按需读取。Rule/Function 计算诊断建议，Action 经批准可在 EAM/CMMS 中创建维护工单；首期不自动控制 PLC。

### 11.3 第三故事：同名异义 → 跨源对齐 → 撤权

CRM 签约客户、ERP 结算客户、售后受益人分别是不同语义身份候选。Term/Concept/IdentityRule 与批准过的 AlignmentAssertion 区分上下文；未经审查的候选不进入权威 Query/Context；撤回某来源授权后需要能证明 ObjectSet、缓存、MCP、派生输出和 Action 均不能继续消费受限信息。

| **10、31** 工程结构与多引擎 | 模块化单体，PG 作为 P0 默认；Graph/Search 通过 Adapter 扩展 | POC 支持初期候选，不是全规模承诺 |
| **11–13、23–24** 领域包/标准/扩展/许可 | Core/Foundation/Domain/Enterprise；开放标准按 Profile | 原则拟冻结；标准/许可需专项签收 |
| **15–16、18、25–26** 术语/审查/质量/Native | Native Model + ChangeSet/锁定审批/质量检查 | V0.2 契约候选，P0-A/B 工程未完成 |
| **27、32** ObjectSet + Security | Typed Query AST、Auth Pushdown、Budget、派生输出安全 | 原则拟冻结；生产 ABAC 未验 |
| **30** Optional OWL Adapter | 选择性导入导出、显式保真等级，不成为发布权威 | 路线拟冻结；P4 可选实现 |

**变更决策原则**：如果真实工厂的超级节点、联邦延迟、持续写入或超大查询超过 PostgreSQL 经济性，先使用真实同口径 POC 和 ADR 比较再升级 Query Physical Plan；不能倒过来为追逐图数据库改变 ObjectSet 的业务身份与接口。真实 ERP 缺少幂等/回执时，不能因希望自动化就放宽 Action 安全。

## 16. 2026-10-17 实施优先级修订：核心 MVP 与 yak-ops 通用认证复用

> **本节为实施优先级说明，不改变 V1.3 的长期产品骨架，也不代表企业生产安全、治理流程已经签收。** 具体代码状态和用户故事详见[实施决策](./implementation/MVP-核心优先与yak-ops认证复用决策-20261017.md)。

- **当前优先级**：以制造质量追溯为业务样例，完成 Native ObjectType/LinkType → 本机脱敏 PG Data Binding → ObjectSet 有界对象集合查询 → 可追踪业务结果，持续用真实数据库和可操作页面验收。已支持的单路径查询仍不能代表通用 ObjectSet。
- **核心下一阶段**：以“一批质量异常影响多个工单/客户订单”为切口，提供真实多结果、稳定去重/排序/分页和明确来源证据，逐步形成 ObjectSet 执行合同。Agent Context/Action 不能掩盖基础对象查询与数据绑定的不完整。
- **通用用户登录与认证非当前 MVP GATE**：#17 OIDC/JWT 已合并，但其外部 IdP 配置不应继续阻塞单人本机测试工作流。本机隔离开发可显式使用 `mvp-local`（无用户隔离，严格 loopback 与测试库限制）；不代表上线安全模式。
- **未来统一复用**：出现真实多人协作/生产身份需求时，优先评估 [yak-ops](https://github.com/weifuwan/yak-ops) 已有 `HttpSession` / 登录 / 用户管理 / Web 认证组件，按兼容性、Apache-2.0 授权、Cookie/CSRF、Session 失效和权限衔接单独验收。不会默认同时维护两套认证体系。OIDC/JWT 仅在被明确验证的企业 SSO 或服务间身份需求下才重评。

这项修订严格区分**现在必须实现的工业本体价值**与**以后复用/集成的企业基础能力**。
