## 1. 范围与结论

本标准第1章明确适用于**标准数字化中的标准本体**，并不等于所有行业企业本体的强制元模型。我们把其中可迁移的工程规则落实到通用本体内核，标准实体、标准文件、章/条/信息单元、制定程序则放到**可选的标准文档本体专业包**中，不污染制造业及企业通用模型。

本次评审识别出 V1.1 的主要缺口：**全球唯一 IRI 与命名空间、规范性附录A的类和属性元数据、数据与对象属性的类型边界、形式化公理的可执行校验、内容与表述形式分离、模块化扩展兼容门禁**。已有方向不等于已实现，不能宣称代码符合国标。

## 3. 附录A关键设计契约

**规范性附录A.1 的实体类型元数据**：IRI、Name、Label、Definition、Properties、SubclassOf、HasSubclass、EquivalentClass。父类、子类和等价类是条件适用，不应将不存在父类一概判为不合格；Label 支持多语言。

**规范性附录A.2 的属性元数据**：IRI、Name、Label、Definition、Domain、Range、TypeOfTerms。其中 TypeOfTerms 对应对象属性与数据属性的明确区分，不能从某次运行值推测属性种类。

**规范性附录A.3 基本数据类型**：布尔型、日期、数值型、文本型、统一资源链接。作为标准文档本体 Profile 的映射基线；企业通用内核可以扩展日期时间、数值精度、持续时间及带单位量值。

IRIPolicy 建议包括 domain_owner、namespace_uri、local_name、semantic_id、release_scope、alias、deprecation 和 collision_check。生产 URI 不得照搬本标准示例的 example.org 地址。IRI 的全球唯一性不意味着自动满足业务实体身份一致性。

## 4. 公理、约束和执行规则不可混同

| 技术对象 | 应承担 | 不应该误用为 |
|---|---|---|
| OWL/RDFS | 类继承、不相交、逆关系及关系语义蕴含 | 必填字段的封闭世界验证 |
| SHACL | 必填、基数、枚举、取值、结构、日期关系等质量校验 | 生产设备行动的安全许可 |
| Domain Rule / Workflow | 质量处置条件、业务状态变更、审批与回执 | 本体语义真值 |
| Action Policy | 独立授权、风险评估、审批与执行门禁 | 图中某个 Action 类可被推理即允许调用 |

**第8.2节的验证实例**：互斥类冲突、唯一标识、唯一值、实施日期与发布日期的时序关系、枚举与范围、功能性关系、版本替代、层级结构和引用关系区分。针对标准文档本体包建立正例、反例、归因报告及版本回归。注意 OWL 的开放世界推理并非“缺值就是不合规”的数据验证语义。

## 5. 标准文档本体专业包建议

标准第6.2章涉及的核心类别可映射到独立 Profile：Standard、StandardizationObject、Stakeholder/Organization/Individual、DomainCategory、ContentElement、StructuralElement、InformationUnit、InformationForm、Object、Characteristic/Constraint、ActionClass、ExternalResource、StandardizationProcess。

这里**信息单元**要和**表述形式**分离：同一技术要求可以在正文、表格、图片等多种介质表达，其语义锚点不随章节调整自动消失。标准中的“行动”表示被标准条款描述的动作/试验步骤，不会天然具有可调用的企业工具权限。真正的 Action Runtime 需要额外的工具绑定、身份授权、风险政策、执行审计。

可利用附录D电池标准容量、测试方法和技术条件的示例构造一个专业用例：产品对象 → 技术特性 → 质量/容量约束 → 检验步骤 → 条款证据 → 质量记录。它属于示例素材，需要经过本项目解析、类型及约束验证后才能进入测试工程。

## 6. 新 ADR 和实施优先级

| 决策 | 推荐方向 | Gate |
|---|---|---|
| ADR-20 IRI 策略 | 内部稳定 semantic_id 与公开 IRI、受控命名空间 | 重命名不换身份、跨包碰撞阻断 |
| ADR-21 形式化编译 | DSL/AST 到 RDF/OWL、SHACL、Turtle/JSON-LD | 静态分析、导出导入与往返 |
| ADR-22 属性与公理 | 显式 DataProperty/ObjectProperty/Axiom 类型 | 不适用的关系特性被拒绝；规则分层 |
| ADR-23 标准文档本体 Profile | 按第6–9章及附录A单独实现 | 只对已实现并测试的 Profile 提符合性证据 |
| ADR-24 模块兼容 | 核心/制造基础/领域/企业包隔离与依赖锁 | 扩展不覆盖核心，变更影响清楚 |

**P0**：IRI/命名空间、元数据契约、类型系统、OWL/SHACL 编译校验、版本门禁及发布测试。

**P1**：可按具体场景选择开发标准文档本体 Profile，建立内容-形式-来源分离的知识锚点及实体/关系样例。

**P2**：标准文本智能提取与 Agent 辅助建模，依旧必须经人工审核与质量门禁。

## 7. 证据等级和符合性边界

标准第9章与规范性附录A对**标准本体范围**具有直接参考/适用价值；附录B、C、D属于资料性附录，不能把里面的所有实例字段错误认定为一律强制。正式符合性审核仍需基于实际标准适用范围、完整实现代码、测试记录、评审签字和版本证据。V1.1 是**产品架构设计**，现阶段只能说“新增条款级设计映射”，不能称“已符合国标”。
